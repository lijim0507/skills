## 1. Development Philosophy

- 规范优先于临时指令
- 优先理解现有代码，再进行修改
- 优先最小化修改范围
- 不允许为了完成需求而引入不必要的复杂度

## 2. Architecture Governance

### 2.1 模块分层规则

模块采用应用层/驱动层双层对外结构：

- `app_<module>.c/.h`：业务逻辑、状态机、跨模块公共 API。
- `<module>.c/.h`：中间层，为模块内使用的，协议或元件的功能逻辑接口实现。
- `drv_<module>.c/.h`：硬件抽象、底层外设操作、模块私有实现。

约束：

- 其他模块只能包含 `app_<module>.h`。
- `drv_<module>.h` 只能被同一模块的 `app_<module>.c` 或对应 `drv_<module>.c` 包含。
- 不要跨模块直接调用 `drv_<module>_*`。
- 不要跨文件直接访问模块内部全局变量；通过 `app_<module>.h` 提供 getter/setter 或事件接口。
- 新增任务、队列、信号量时，同步修改 `app_rtos.c/.h`，不要在业务模块内直接创建 RTOS 对象。
- 遵循项目既有架构
- 不允许未经批准改变模块边界
- 不允许未经批准引入新的架构层级
- 公共接口变更必须说明影响范围

## 3. Code Quality

### 3.1 命名和代码风格

- 禁止使用中文拼音命名。
- 禁止单字母变量名，`for` 循环中的 `i`、`j`、`k` 等短循环变量除外。
- 避免在名称中使用数字编号，除非编号本身有明确业务或协议含义。
- 文件名：`snake_case.c`、`snake_case.h`。
- 函数、变量、结构体成员使用下划线分隔风格，允许在已有代码风格需要时使用下划线 + 驼峰，但新代码优先使用 `snake_case`。
- 应用层函数：`app_<module>_<action>()`。
- 驱动层函数：`drv_<module>_<action>()`。
- 局部变量：`snake_case`，指针变量建议使用 `p_` 前缀。
- 文件内私有全局变量：`static`，命名使用 `g_` 前缀；对外开放的全局变量必须在对应头文件中 `extern` 声明。
- 宏：`ALL_CAPS_WITH_UNDERSCORES`。
- 枚举值：`ALL_CAPS_WITH_UNDERSCORES`。
- 结构体和枚举类型：`snake_case_t`。
- 缩写优先使用完整单词或业内常见缩写；自定义缩写或过长名称的首字母缩写必须在声明处注释说明完整含义。
- 头文件保护：`#ifndef __APP_MODULE_H` / `#define __APP_MODULE_H` 风格，和现有文件保持一致。
- C++ 兼容头文件使用 `extern "C"` 包裹声明。
- 系统/标准库头文件放前面，项目头文件放后面，保持局部有序。
- 函数无参数时必须显式写 `void`，不要写空参数列表。
- 非特殊情况不要使用 `void *` 作为接口参数；参数调用处或接口内部必须检查参数合法性。
- 函数参数超过 5 个时，优先考虑整合为结构体或拆分函数；有输出参数时，输入参数放前，输出参数放后。

### 3.2 头文件、宏和文件组织

- 每个 `.c` 文件原则上应有同名 `.h` 文件；仅文件内私有实现或第三方组件按现有结构处理。
- 禁止循环依赖头文件。
- 所有对外开放的接口必须在头文件中显式声明；不要在使用方 `.c` 文件中手写 `extern` 调用外部函数。
- 头文件中只放声明、宏、类型定义和 `extern` 声明，不放函数实现或变量定义。
- 相同类型的声明放在同一区域，推荐顺序为宏、类型、外部变量、函数声明。
- 函数式宏必须带括号调用形式，即使没有参数也写成 `XXX()`。
- 函数式宏的参数和整体表达式必须使用完备括号，例如 `(((a) < (b)) ? (a) : (b))`。
- 避免使用多语句函数式宏；宏中不要使用 `return`、`goto`、`continue`、`break` 等改变流程的语句。
- 不要把带副作用的表达式传给函数式宏，例如 `SQUARE(a++)`。

### 3.3 可维护性要求

编写代码时必须留下必要注释，但不要写重复代码本身的空泛注释。公共接口、公共结构体、公共宏和函数定义处优先使用 Doxygen 风格注释，说明用途、参数、返回值、单位、生命周期或调用上下文。

必须注释的内容包括：

- 任务、队列、信号量之间的时序关系和阻塞策略。
- 实时性相关取舍，例如“队列满时丢弃而不是阻塞”的原因。
- 硬件 IO、协议格式、二进制数据布局、文件命名规则、单位和缩放范围。
- 错误恢复流程、状态机跳转条件和重试策略。
- 暂时无法实现或依赖硬件确认的字段、宏和占位逻辑。
- 注释只能位于代码上方或右方，不要把注释放在语句中间或被注释代码的下方。
- 修改代码时必须同步修正已经失真的注释。
- 不用的代码段应删除；少量调试代码临时注释时必须写明原因。
- `switch` 的 `case` 如需贯穿且内容非空，必须添加 `/* fall-through */` 注释。
- 除非能用英文准确表达，否则项目内注释优先使用中文。
- 复杂私有函数也应在实现处写简短说明；重复代码块应抽取为函数，避免复制粘贴维护。

## 4. Testing & Verification

- 行为变更必须有对应的验证
- 必须执行相关测试
- 无法执行测试时必须说明原因
- 不允许将未验证的代码宣称为验证通过

## 5. AI Development Governance

- 修改代码前必须理解相关上下文
- 不得擅自扩大需求范围
- 不得擅自修改无关文件
- 不得伪造编译、测试结果
- 涉及架构、公共接口、依赖变更时必须说明
- 需求存在关键歧义时必须先澄清

## 6. Change Management

- 明确每次修改的目标和范围
- 记录重要设计决策
- 重大架构变更必须经过人工审核
- 代码实现必须符合对应 Spec 和 Plan

## 7. Governance

- 规范修改必须经过团队评审
- 规范与项目实际情况冲突时必须明确处理
- 定期审查规范的有效性
