# 示例：一次变更轮走完整流程

用真实项目里的 r2 做样例：**面板灯语义重排 + 脚位 47**。

## 变更请求

> 「面板灯语义改一下：白=上电/空闲、蓝=测试中、绿/红=RESULT 不变、灭态废除。另外硬件改版了，脚位从 48 改到 47。」

## 第一步：判落点

判据：改它，验收场景变没变？

| 问                 | 答                                                                              | 结论                   |
| ------------------ | ------------------------------------------------------------------------------- | ---------------------- |
| 验收场景会不会变？ | US4 验收场景 3「回到 IDLE，白灯常亮」——原语义是「灭=IDLE」，现在是「白=IDLE」 | **会变 → spec** |

触到了 spec，已经是最高处；但**方案也变了**（脚位 48→47），所以落点那一行里还要记上**同时触及 plan**。

> **兜底规则**：如果当时判不出来，按上游处理——当成 spec。

## 第二步：写受理单（五栏）

写进 `03-tasks.md` 的新变更轮段：

```markdown
## 变更轮（2026-09-18 r2：面板灯语义重排 + 脚位 47）

> - **落点**：spec（最高处）｜同时触及 plan（脚位 48→47、灯态实现手段）
> - **验收场景**：有变化 ｜ US4 验收场景 3「回到 IDLE，白灯常亮」由「灭态」改为「白常亮」
> - **重走范围**：门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge
> - **门 1**：approve ｜ 裁决人：张三 ｜ 日期：2026-09-18
> - **门 2**：approve ｜ 裁决人：张三 ｜ 日期：2026-09-18
> - **判定依据**：`01-spec.md` US4 验收场景 3 的语义变更（判据：改它验收场景变没变）
> - **处置记录**：见 `04-converge.md` 变更轮
```

## 第三步：机器兜底（写完受理单就跑）

```text
$ python <技能目录>/scripts/check_intake.py 03-tasks.md
受理单校验通过

$ python <技能目录>/scripts/check_landing.py 01-spec.md 03-tasks.md --since v1.0
提示：验收场景确实变了（用户故事 4 - ...），受理单声明一致
落点对照通过（无阻断性不一致）
```

门结论也在这里验：

```text
$ python <技能目录>/scripts/check_gate.py 03-tasks.md --spec 01-spec.md --plan 02-plan.md
门记录校验通过
```

如果门记录还写着 `待审`（或没填裁决人、日期），这个脚本会直接报错——**这正是「门是阻塞点」的机械形态**：没批就过不去。

这几个脚本都不替你判断，只保证两件事：**声明之间不打架**、**声明与事实不打架**。

## 第四步：随重走路径走

**落点是 spec，所以第一站是门 1。门是阻塞点**：改完 spec 必须**停下**，把受理单与 spec 一起交给用户审批，拿到明确 approve 才继续。

```text
门 1（审 spec 的改动；未动部分沿用上次结论）
   ↓ 停下等人：approve
02-plan 修订（脚位 48→47 进硬件资源分配表；灯态实现手段）
   ↓
门 2（审 plan 的改动）
   ↓ 停下等人：approve
03-tasks 追加变更轮段的任务
   ↓
analyze ── 查到「任务-规格矛盾」：T026/T029 描述的还是旧的 off 态
   ↓ 回上游处理：作废 T026/T029
checklist ── 门 1 清单只读复核：全勾才继续
   ↓
implement（T034 / T035）
   ↓
converge ── 发现数递减 → Converged
```

## 关键的三处

### 1. analyze 抓到了「任务-规格矛盾」

spec 的 FR-040 现在写着「无灭态；白=空闲、蓝=测试中」，但 `03-tasks.md` 里 T026 还写着「busy/pass/fail/**off** 四态」、T029 还写着「**白=FLASH+CAN 全程**、**灭=IDLE**」。

**这是标准的任务-规格矛盾**——`analyze` 会直接标出来。

> 这正是「变更轮也要跑 analyze」的价值。只跑 `converge` 抓不到它：`converge` 查的是「实现有没有背叛文档」，而这是「**文档内部自相矛盾**」。

### 2. 作废要三处标记

```markdown
- [~] T026 [P] [US1] ~~面板 WS2812（busy/pass/fail/off 四态一次性设置）~~ | FR-040/041
      ⤷ r2 作废：灭态废除、busy 改蓝，被 T034 取代
```

- `[~]` 换掉 `[x]`
- 内容划删除线（任务号与 FR 编号留在外面，保持可检索）
- 下一行 `⤷` 说明被谁取代、为什么

同时在变更轮段登记一份作废清单。

**为什么不能直接删掉 T026/T029**：`Done When` 是「全部 `[x]` 或 `[~]`，无 `[ ]`」。删掉等于抹掉历史；留着 `[x]` 等于状态是错的——**过时的 `[x]` 比 `[ ]` 更有害**：`[ ]` 会提醒人，`[x]` 会让人以为做完了。

### 3. 声明是可被证伪的

如果这次改动其实没动验收场景却申报成 spec，`check_landing.py` 会提示；反过来**把真实的验收场景变更申报成 plan / 仅实现，它会报错**：

```text
错误：01-spec.md 的验收场景相对 HEAD 有变化（用户故事 4 - ...），
但最新受理单落点是「仅实现」、验收场景栏是「无变化」
——验收场景变了就是 spec 落点，应重判并按 spec 重走（判不准按上游）
```

这是 2.0.0 缺的那一环：**判断由人做，声明由脚本兜底。**

## 那个真实教训

r2 当时没有写落点，于是**一个未经门 1 的需求变更溜了过去，躺了近一个月才被发现**——完整经过见 `references/rationale.md`。

这也正是受理单必须写全五栏的原因：没有声明，就没有可核对的东西。现在 `check_intake.py` 查三者自洽、`check_landing.py` 查声明与 diff，同类问题在提交受理单的那一刻就会暴露。
