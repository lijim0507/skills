# 起步：绿地与棕地

## 前提：宪法和 spec 都是「提取」出来的，不是「发明」的

宪法不是凭空写的——原则来自需求文档中散落的隐含约束，以及组织级知识库（如 `AGENTS.md`）的通用原则。宪法的职责是把这些隐含约束**显式化、编号化、可判定化**。

spec 同理：它是从已有素材里**挖出来、摆整齐**的，不是坐下来凭空撰写的。

素材有三类：**需求文档**、**既有实现**、**组织级知识库**。

## 绿地（新项目，有需求、无代码）

```text
提取宪法（从需求里挖隐含约束 + 组织级原则）→ 用户 ratify
   ↓
写 spec（what/why，未明处标 [NEEDS CLARIFICATION]）
   ↓
门 1（人，阻塞点）
   ↓
写 plan（how，含 Constitution Check）
   ↓
门 2（人，阻塞点）
   ↓
拆 tasks → 进入正常流程
```

**宪法的写法要求**：

- 每条原则必须**可判定**——能直接回答「这个方案是否违反」
- 每条注明**出处**（需求第几节 / 组织级原则第几条）
- 不可协商的标 `NON-NEGOTIABLE`
- **具体值不进宪法**（引脚号、参数属于 plan）

## 建成之后：先清理，再自检

模板里的示例段（如 `03-tasks.md` 的示例变更轮）**用完就删**——校验器会把示例变更轮当成真受理单、把示例任务当成真任务。

```text
python <技能目录>/scripts/check_spec.py   <项目>/SDD/01-spec.md
python <技能目录>/scripts/check_intake.py <项目>/SDD/03-tasks.md
python <技能目录>/scripts/check_tasks.py  <项目>/SDD/03-tasks.md
python <技能目录>/scripts/check_gate.py  --spec <项目>/SDD/01-spec.md --plan <项目>/SDD/02-plan.md
```

门 1 的清单里挂着「`check_spec.py` 无实现细节警告」，所以这个自检不是可选项，是门 1 的评审材料。
门记录在**没批之前就是「待审」**，`check_gate.py` 会因此报错——这正是它该有的状态：门是阻塞点；批准后把结论改成 `approve` 并填上裁决人与日期，脚本才会放行。

## 棕地 / 回溯（已有代码或已做完的项目，没有 SDD 文档）

关键差别：**spec 是以「实现」为事实源反推出来的**，所以它描述的是「**现在是什么**」，而不是「**应该是什么**」。

### 陷阱：不许用「改规格」掩盖实现缺陷

反推时如果发现实现与应有规格不符（比如反推出「命令码表是 0x02~0x06」，但实现里是另一套），**不能顺手把 spec 改成实现的样子让它自洽**。

那正是「就地改到通过」。

### 正确做法：偏差进「待办与偏差登记」

`02-plan.md` 里设「待办与偏差登记」一节，反推时把「实现与应有规格对不上」的地方登记进去——**不掩盖、不消灭，让它显式存在**。

```text
反推实现 → 得到 spec / plan
   ↓
发现的偏差 → 进「待办与偏差登记」
   ↓
逐条确认偏差判定（只确认偏差，不确认正常内容）
   ↓
门 1 → 门 2
   ↓
拆 tasks（含清理待办的任务）
```

### 为什么只逐条确认「偏差」

- 正常内容：只是抄写，逐条确认没有信息量
- **偏差**：「这条是实现错了，还是需求本来就是这样」——**只有人知道，agent 判不了**

所以回溯的价值就在把偏差捞出来；逐条确认偏差，正是防止**把实现里的错误当成需求固化下来**。

## 宪法之后要改怎么办

宪法是链的最上游，改动落点是 **宪法**：

```text
Governance 修订（记版本号 / 批准日期 / 修订理由）
   ↓
按 `SKILL.md` 落点表中「宪法」一行的重走范围走
```

受理单的落点栏写 `宪法`，重走范围从 `Governance 修订` 起。`check_intake.py` 对它的要求与 spec 相同（必须含门 1、门 2）。

## 回溯建档本身也是任务

在 `03-tasks.md` 里留一条：

```text
- [x] T0xx 回溯 SDD 流程建档于本目录（00 / 01 / 02 + 子件 / 03 / 04）| 流程
```
