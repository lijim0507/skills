# 角色分工，以及多 agent 怎么用

## 这套流程是团队流程的浓缩

| 角色 | 干什么 | 对应文档 |
| --- | --- | --- |
| 产品 | 提需求、定优先级、判验收、确认外部契约 | `00-constitution.md`、`01-spec.md`（含外部契约） |
| 技术负责人 | 出方案、检验可行性、答宪法、确认外部契约 | `02-plan*.md`、`02-plan-contracts.md`（内部契约） |
| 管理者 | 拆任务、分配 | `03-tasks.md` |
| 实现者 | 按任务写代码 | 代码 |
| 检查者 | 文档互查、收敛检查 | `03-tasks.md` 的检查节、`04-converge.md` |
| 验收人 | 按场景与外部契约实测签字 | `04-converge.md` |

## 一个角色可能在同一个人身上

个人项目里产品、技术负责人、验收人常是同一人。这个隐喻仍有价值——它告诉你**每次只戴一顶帽子**：

- 写 `01-spec.md` 的产品行为时假装不懂技术，只描述行为；写外部契约时只写消费者能验证的承诺，不写内部实现
- 写 `02-plan.md` 时才允许谈内部实现细节（资源、依赖、时序、模块划分等）
- 审门 1 只看需求与外部契约，审门 2 只看方案与内部契约，不要在一锅里审
- 外部契约由产品和技术负责人共同确认；技术负责人不能单方面改产品承诺

## agent 负责发现，人负责裁决

扮演角色的 agent 在门前产出**审查意见**（哪里可疑、哪里没写清、哪条 FR 没有任务覆盖），由人读意见后签 `approve`。**人保留唯一的否决权，agent 不代签。**

## 多 agent 的真正红利是独立上下文

多开一个 agent 扮演评审，价值不在于「多个人」，而在于**换一份独立上下文**：它没读过你和实现 agent 的讨论过程，只能看文档。

**所以它恰好就是那个「不知道来龙去脉的执行者」**——它能测出文档自不自包含、任务写得够不够细。这是同一个 agent 自查永远做不到的。

## 任务要自包含

团队里任务书是**沟通媒介**（执行者不在你脑子里）。单人 + agent 时，任务的用途变成两件事：划出可勾选的边界（防止顺手多改）、让覆盖映射可核对。

由此得出粒度的判据：**小到能判定完成**。检验方法——一个不知道来龙去脉的执行者，只看这一条任务，能不能做完并自己判定做完没做完。

## 分工的边界

- 扮演评审的 agent **不能**签 approve
- 实现 agent **不能**勾开工前检查清单，也**不能**改它
- 任何 agent **不能**「就地改到通过」——发现问题必须回到拥有它的地方解决（见 `references/gates.md`）
