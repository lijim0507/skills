# 三种帽子：产品经理、技术总监、任务负责人

## 这套流程是团队流程的浓缩

SDD 不是「写三份文档」，而是**三次角色交接**。每顶帽子只回答一个问题，只对一种结果负责：

| 帽子 | 只回答 | 产物 | 不做什么 |
| --- | --- | --- | --- |
| 产品经理 | 为谁解决什么问题，什么算做对了？ | `01-spec.md` | 不选技术方案、不拆任务、不写实现细节 |
| 技术总监 | 在现有约束下怎么做，为什么这样最合适？ | `02-plan*.md` | 不改需求、不替产品定优先级、不写代码 |
| 任务负责人 | 谁在什么边界内做什么，怎么算完成？ | `03-tasks.md` | 不重新设计架构、不扩大需求、不只写“实现 XX” |
| 实现者 | 按工单交付可验证的结果 | 代码 + 验证证据 | 不擅自改需求或架构；发现缺口回到上游 |
| 验收人 | 按 spec 在真实环境判定 | `04-converge.md` | 不用“代码看起来对”代替实测 |

一个人可以同时戴多顶帽子，但**一次只戴一顶**。切换帽子时，先写完交接摘要，再换视角；不要把产品、技术、任务三种判断混在同一段话里。

## 三段交接

| 交接 | 上游必须交出 | 下游必须回应 | 卡在哪 |
| --- | --- | --- | --- |
| 产品 → 技术 | 问题、目标消费者、非目标、外部契约、验收方式 | 逐条可行性结论；不可行项回产品，不私自降级 | 门 1 |
| 技术 → 任务 | 方案总览、模块边界、实施顺序、验证手段、风险与回滚 | 任务卡；每条任务能独立分配、独立判定完成 | 门 2 |
| 任务 → 实现 | 任务分配说明、执行批次、任务卡、完成判据 | 按范围交付；发现缺口停下回上游 | 任务交接检查 |
| 实现 → 验收 | 代码、验证证据、收敛结论 | 按 `01-spec.md` 的场景和契约在真实环境逐条跑 | 验收 |

交接摘要是**压缩**，不是复述。只写下一顶帽子必须知道、但 diff 里看不出来的判断。

## 每顶帽子的质量判据

### 产品经理：spec 能不能被验收

- 每个故事都有明确的消费者、问题、价值和优先级理由
- 验收场景是 Given / When / Then，结果在外部可观察
- 非目标写清楚；不做什么和做什么同样重要
- 没有框架、模块划分、表结构、内部参数等技术选择
- 有外部消费者时，外部契约可被消费者独立验证
- 没有外部消费者时，明确写“无外部契约”，不要留空

**越位信号**：spec 里出现“用 Redis”“拆成微服务”“加一个索引”“走某框架”。这些是技术总监的判断，不是产品承诺。

### 技术总监：plan 能不能被实施

- 对每条 FR / 外部契约给出可行性结论：可行 / 有条件 / 不可行
- 不可行项回到 `01-spec.md` 改需求，不在 plan 里偷偷降级
- 模块边界、依赖方向、数据所有权、写权限清楚
- 关键决策有备选方案与否决理由
- 性能、安全、可靠性、可观测性、成本、兼容性有方案或明确不做
- 验证手段可执行：环境、数据、工具、命令、判据都写清
- 迁移、发布、回滚、监控有安排
- 不重复 spec 的需求和外部契约

**越位信号**：plan 里出现“用户其实不需要这个”“这个需求先砍掉”。这是产品判断，必须回门 1。

### 任务负责人：tasks 能不能被分配

- 每条任务有唯一编号，挂 `FR-0xx`、外部契约项、风险项，或显式标 `| 流程`
- 任务卡写清：执行者、目标、范围、输入、产出、完成判据（DoD）、验证、依赖、是否可并行
- 任务范围不重叠；依赖无环；执行批次和进入条件清楚
- 粒度判据：**一个不知道来龙去脉的执行者，只看这一条任务卡，能做完并自己判定做完没做完**
- 任务不是方案复述，也不是“实现登录”这种没有边界的愿望

**越位信号**：任务卡里重新论证架构、改模块边界、扩大需求。发现方案问题应回 `02`，不是在下游私了。

### 实现者：代码能不能对得上工单

- 只改任务卡允许的范围，不顺手扩大
- 每完成一条任务，勾选 `[x]` 并留下验证证据
- 发现 spec / plan 有缺口，标 `blocked` 并说明卡在哪、等谁
- 不把“就地改到通过”当成解决

### 验收人：结果能不能在真实环境成立

- 按 `01-spec.md` 的验收场景逐条跑，不用“代码看起来对”代替
- 外部契约在真实消费者视角验证
- 记录验证环境、数据、命令和证据
- 不通过就回上游，不在验收环节改需求

## agent 负责发现，人负责裁决

扮演角色的 agent 在门前产出**审查意见**（哪里可疑、哪里没写清、哪条 FR 没有任务覆盖），由人读意见后签 `approve`。**人保留唯一的否决权，agent 不代签。**

## 多 agent 的真正红利是独立上下文

多开一个 agent 扮演评审，价值不在于“多个人”，而在于**换一份独立上下文**：它没读过你和实现 agent 的讨论过程，只能看文档。

**所以它恰好就是那个“不知道来龙去脉的执行者”**——它能测出文档自不自包含、任务卡写得够不够细。这是同一个 agent 自查永远做不到的。

## 分工的边界

- 扮演评审的 agent **不能**签 approve
- 实现 agent **不能**勾任务交接检查清单，也**不能**改它
- 任何 agent **不能**“就地改到通过”——发现问题必须回到拥有它的地方解决（见 `references/gates.md`）
- 产品、技术、任务三顶帽子可以由同一个人戴，但门 1 和门 2 必须分别停一次，不能合并成一句“都看过了”
