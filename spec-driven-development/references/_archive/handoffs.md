# 交接：每顶帽子交出去什么

## 交接不是摘要，是压缩

下游不需要重读全文，但必须知道**这一步为什么这样做、边界在哪、什么不能动**。交接摘要只写 diff 里看不到的判断：

- 上游做过什么取舍，为什么
- 哪些约束是不可妥协的
- 哪些地方下游可以自行决定，哪些必须回来问
- 什么算完成，什么算越界

不要把正文再抄一遍。如果交接摘要删掉后下游仍然能开始工作，说明它写得太多了；如果删掉后下游必须来问，说明它写少了。

## 产品 → 技术：spec 的交接段

放在 `01-spec.md` 的「交接给技术总监」节，门 1 之后写：

```markdown
## 交接给技术总监

- 核心问题：<谁在什么场景下遇到什么问题>
- 产品定位：<消费者 + 场景 + 问题 + 价值；细节见 01-spec>
- 必须兑现的外部契约：<契约项编号或“无外部契约”>
- 不可妥协的约束：<合规、期限、兼容性、预算、既有系统>
- 验收方式：<在什么环境、按哪些场景、看什么证据>
- 明确不做：<N1 …，防止方案膨胀>
- 需要技术判断的取舍：<产品知道有取舍但不应由产品单方面定的点>
```

技术总监读完要能回答：这些要求是否可实现？哪些有条件？哪些必须回产品改？回答写进 `02-plan.md` 的「需求可行性核对」。

## 技术 → 任务：plan 的交接段

放在 `02-plan.md` 的「交接给任务拆解」节，门 2 之后写：

```markdown
## 交接给任务拆解

- 方案一句话：<整体怎么做>
- 模块与边界：<这次涉及哪些模块，各自负责什么，写权限在哪>
- 实施顺序 / 批次：<先做什么、哪些可并行、进入条件>
- 每条 FR 的落点模块：<FR-001 → 模块 A；FR-002 → 模块 B>
- 验证环境与命令：<在哪儿跑、跑什么、看什么>
- 主要风险与回滚：<最可能出问题的地方，怎么退>
- 需要产品确认的取舍：<技术上有条件、但会影响产品承诺的点>
```

任务负责人读完要能回答：每条需求落在哪个模块？先做哪一批？每条任务做完怎么验？回答写进 `03-tasks.md` 的任务卡。

## 任务 → 实现：tasks 的分配说明

放在 `03-tasks.md` 开头的「任务分配说明」节：

```markdown
## 任务分配说明

- 执行者开始前先读：<01 的哪些节、02 的哪些节；不要要求读全文>
- 代码范围 / 分支 / 目录：<允许改哪里，禁止改哪里>
- 通用完成标准：<所有任务共同遵守的 DoD>
- 验证命令 / 环境：<怎么跑，需要什么依赖>
- 汇报格式：<完成任务时回传什么证据>
- 阻塞时找谁：<遇到 spec / plan 缺口找谁，不要自己猜>
```

任务卡是执行者真正使用的工单。索引行只用于扫描和脚本检查；**非平凡任务都必须有任务卡**。

### 任务卡模板

```markdown
### T001 <标题>

- 归属：FR-001 / 外部契约项 / 风险项 / 流程
- 执行者：<角色 / 人名>
- 目标：<这条任务要交付什么结果，不是“写什么代码”>
- 范围：<允许改动的模块 / 文件 / 目录；明确不做什么>
- 输入：<上游产物、数据、环境、依赖>
- 产出：<代码、配置、文档、测试、证据>
- 完成判据（DoD）：<什么条件全部满足才算完成>
- 验证：<命令 / 环境 / 预期输出 / 证据放在哪里>
- 依赖：<无 / T000；依赖没完成时不能开始>
- 可并行：[P] / 否
- 风险 / 回滚：<可能踩的坑，出问题怎么退>
```

## 任务拆解的四个检查

1. **能不能独立开始**：执行者只看任务卡和指定章节，能不能动手？
2. **能不能独立结束**：完成判据是否可观察、可验证，不依赖“问作者”？
3. **边界会不会打架**：两条任务是否改同一处、互相覆盖？依赖是否成环？
4. **有没有丢需求**：每条 FR / 外部契约项是否至少被一条任务覆盖？

四个问题有一个答不上来，就回 `02` 或 `01`，不要在 `03` 里用一句“实现 XX”糊过去。

## 实现 → 验收：交付说明

实现完成后，`04-converge.md` 要能让验收人独立复跑：

- 本轮范围、落点、轮次
- 每条验收场景的结果
- 每条外部契约的验证结果
- 验证环境、命令、测试数据、证据位置
- 未通过项和回退位置
- 结论：`Converged` / `Tasks appended`

验收人不需要读实现过程，只需要能按这份说明复现结论。
