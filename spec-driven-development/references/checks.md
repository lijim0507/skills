# 机器检查：analyze、任务交接检查、converge

这三站不是人审，但有一条共同底线：**不允许「就地改到通过」**。发现问题时它们唯一能做的是**把问题变成新任务交给人**。

## analyze（S4）——文档互查

对 `01-spec.md`（含外部契约）/ `02-plan*.md` / `03-tasks.md` 做跨产物一致性分析，报告冲突、缺口与歧义：某条任务没有对应需求、某条 FR 没挂在故事下、方案与规格矛盾、契约与数据模型互斥、任务卡与索引行不一致。

- **唯一的写权限**：`03-tasks.md` 的「analyze 交叉检查」节。**不改需求、方案、任务内容**——「只读」的确切含义是「不修改被检查的内容」，不是「不写任何文件」
- 发现问题**回上游修**：需求问题回 `01`，设计问题回 `02`，任务问题回 `03`
- 修完**重跑 analyze 直至干净**（该节未闭合项 = 0）
- **每轮发现数必须严格递减。** 某轮不降反增 → 立即停下回上游：发现数反弹说明在打转，而打转通常不是实现的问题，是 **spec / plan 本身有洞**

## 任务交接检查（S5）——能不能开工

`analyze` 查的是「文档自不自洽」，这一站查的是「现在能不能动手」，两者不是一回事：

- 每条 FR / 外部契约项都有任务覆盖
- 任务依赖无环、无指向不存在任务的依赖
- 每条外部契约有可执行的验证手段
- 验收手段可执行：目标环境可用 / 依赖就绪 / 测试数据与工具就绪
- 每条非平凡任务都有任务卡，卡里有执行者、目标、范围、输入、产出、完成判据（DoD）、验证、依赖
- 任务范围不重叠，边界和写权限清楚
- 执行环境、分支、验证命令、汇报方式已就绪
- 没有 `blocked` 未解

**清单由评审者勾**。`implement` 对它**只读**：只能统计已勾 / 未勾，发现有未勾就**停下询问**，不得自己打勾，也不得修改清单。

## converge（S7）——实现 vs 文档

对照 `01-spec.md`（含外部契约）/ `02-plan*.md` / `03-tasks.md` 评估**实现**，确认没有遗漏。

- **只追加**：从不编辑或删除代码或文档正文；唯一写入是往 `03-tasks.md` 追加任务
- 结果二选一：
  - **Converged**——无缺口。判据：除本次追加外，`03-tasks.md` **逐字节不变**
  - **Tasks appended**——有缺口，追加到 `03-tasks.md` 的「收敛追加」段 → 回 S6 再 implement → 再 converge
- 结论写进 `04-converge.md`（本轮收敛结论，不做累积台账）

## 校验脚本

在**技能目录**里，不在目标项目里。只要 Python 3 标准库。

```bash
python <技能目录>/scripts/check_spec.py  <项目>/SDD/01-spec.md    # 规格结构与编号
python <技能目录>/scripts/check_tasks.py <项目>/SDD/03-tasks.md    # 任务、任务卡与开工前检查
python <技能目录>/scripts/check_chain.py <项目>/SDD                # 故事 → FR → 任务，查断链
python <技能目录>/scripts/check_plan.py  <项目>/SDD                # 模块划分、契约引用、依赖环
```

| 脚本               | 保证什么                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| `check_spec.py`  | 章节齐全；每条故事有验收场景；FR / SC 编号连续无重复；门 1 结论行                              |
| `check_tasks.py` | 任务行格式与编号；任务状态统计；每条任务挂 FR 或显式标`| 流程`；任务卡字段（执行者 / 目标 / 范围 / 输入 / 产出 / DoD / 验证 / 依赖）；开工前检查的勾选统计 |
| `check_chain.py` | 跨文档链条不断：每条 FR 都挂在故事下、都有任务覆盖；任务引用的 FR 真实存在；各文档有修订记录节 |
| `check_plan.py`  | `02-plan.md` 有模块划分；`02-plan-contracts.md` 可选（有则查模块清单/依赖方向/契约、引用与依赖环）；技术总监关键节是否齐全 |

回归样例：`examples/todo-cli/SDD`（四道检查全过）；改模板或脚本后先跑它。

**脚本只查机械事实，不判语义。** 没有哪个脚本判断「需求写得好不好」「落点判得对不对」「任务卡写得够不够独立」——那是人的判断。脚本只保证两件事：**声明之间不打架、声明与事实不打架。**

**领域相关的实现细节判断不归脚本**：同一个东西在不同领域可能是外部契约，也可能是内部实现，见 `references/domains.md`。

**外部契约是否完整、是否可验证，由门 1 人工判断**；脚本只查结构，不判断契约语义。

**模块划分是否合理由门 2 判断**；`check_plan.py` 只查结构、引用和依赖环，不判断模块粒度好不好；层名/角色名只做提示。

**无法运行脚本时不能默认通过**：改为人工检查，并把结论写进相应的门小节或检查节。
