# 落点判定与受理单

> 落点表与重走范围表的**权威出处是 `SKILL.md` 的「流程模型（唯一权威）」**。本文件只讲怎么用、为什么这么设计，不复述那两张表。

## 判据与问法

判据只有一条：**改它，验收场景变没变？** 依次问，第一处「会变」的就是落点——问法见 `SKILL.md` 的落点表（宪法 → spec → plan → tasks → 仅实现）。

## 为什么锚点是「验收场景」而不是「需求」

「需求会不会变」是个没法直接比对的概念——同一次改动，有人觉得是需求变更，有人觉得只是实现调整。

「**验收场景会不会变**」则可判定：验收场景写在 `01-spec.md` 的用户故事里，格式固定、可观察、可测试，**diff 一下就知道**。

| 例子 | 验收场景 | 落点 |
|---|---|---|
| 引脚 48→47 | US4 验收场景 1/2/3 一个字不变 | **plan** |
| 灭态废除、白=空闲、蓝=测试中 | 验收场景 3「回到 IDLE，白灯常亮」的语义变了 | **spec** |
| 把 spec 里含糊的一句话写清楚（如「灭态灯」订正为「灭态」） | 验收场景一个字不变 | **澄清** |

**额外好处**：验收场景可脚本比对，所以落点判定不是纯口头承诺——「这个改动改没改到验收场景」这一问，机器能替你回答（见下方「机械兜底」）。

## 兜底：判不准按上游

任何一步判不准 → 当成 **spec** 处理。

理由：判错方向的代价**不对称**。

| 误判 | 后果 |
|---|---|
| spec 变更 → 误判成 plan | **一个需求变更未经审批就溜过去了**（失控） |
| plan 变更 → 误判成 spec | 多走一遍全流程（浪费，但不危险） |

## 跨多层取最高

同一次变更同时触到多层时，按**最高**那层处理（宪法 > spec > plan > tasks > 仅实现）。

例：面板灯语义重排（spec）+ 脚位 48→47（plan）→ 按 spec 处理，重走范围覆盖到门 1。

## 澄清：改的是措辞，不是需求

改 `01-spec.md` 里的文字（错别字、术语统一、把含糊的句子写清楚），而**验收场景一个字不变** → 落点 **澄清**，重走范围 `门 1 → analyze`。

为什么单立一档：没有它，这一问（验收场景变没变？方案变没变？）连着全是「否」，改动会被判成「仅实现」，重走范围只剩 `converge`——把一次文档订正塞进「实现 vs 文档」的收敛检查，是错的落点。

为什么仍然要过门 1：改的是 spec，读它的还是人；而「我以为只是澄清、其实改了语义」正是最需要人看一眼的地方——`check_landing.py` 也会在验收场景真的变了时报错。

## 受理单（五栏 + 门结论行）

判定完落点后，写进 `03-tasks.md` 新增变更轮段的开头。**受理单的字段与格式以本节为准**（`SKILL.md` 只列字段；`examples/change-round.md` 是同一格式在具体项目上的展开）：

```markdown
## 变更轮（2026-09-18 r2：面板灯语义重排 + 脚位 47）

> - **落点**：spec（最高处）｜同时触及 plan（脚位 48→47）
> - **验收场景**：有变化 ｜ US4 验收场景 3「回到 IDLE，白灯常亮」由「灭态」改为「白常亮」
> - **重走范围**：门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge
> - **门 1**：approve ｜ 裁决人：张三 ｜ 日期：2026-09-18
> - **门 2**：approve ｜ 裁决人：张三 ｜ 日期：2026-09-18
> - **判定依据**：`01-spec.md` US4 验收场景 3 的语义变更
> - **处置记录**：见 `04-converge.md` 变更轮
```

每栏为什么必须有：

五栏都不可省（重走范围里经过的门，再加一条结论行）：

| 栏 | 为什么必须有 |
|---|---|
| 落点 | 决定重走范围；写出来才能被人审、被脚本校验。**同时触及哪几层也写在这一行**，说明为什么不只重走一处 |
| 验收场景 | 判据的落地：`有变化` / `无变化`。它是**可被证伪的声明**——填「无变化」却改了场景，脚本与 diff 都会抓 |
| 重走范围 | **可机器校验**：落点写 spec 却没含门 1 → 矛盾 |
| 门 N | 重走范围里经过的门各一条：`approve` + 裁决人 + 日期（未批准写 `待审`）；`check_gate.py` 校验，agent 不得自批 |
| 判定依据 | 指向具体验收场景，让判定可复核 |
| 处置记录 | 链到 `04-converge.md` 的变更轮，闭合追溯 |

**不要另开「请确认落点」的停顿**：落点决定重走范围，而重走范围的第一站就是一道门——落点是 spec 就过门 1，是 plan 就过门 2，受理单**随第一道门一起受人审**。

## 机械兜底：声明要自洽，还要与 diff 对得上

判断由人做，脚本不替人判断；脚本只保证**声明之间不打架**、**声明与事实不打架**：

| 脚本 | 保证什么 | 何时可跑 |
|---|---|---|
| `check_intake.py` | 五栏齐全；落点 ↔ 重走范围 ↔ 验收场景 三者自洽（落点为 plan / tasks / 仅实现 / 澄清 时，「验收场景」必须是「无变化」；落点为 澄清 时重走范围含门 1、不含门 2） | 任何时候（离线） |
| `check_landing.py` | 受理单声明的「验收场景 无变化」与 `git diff` 的真实改动对得上；真的改了验收场景却没按 spec 处理 → 报错 | 有 git 时 |

无法运行 `check_landing.py`（不是 git 仓库、没有基线）时**不能默认通过**：改为人工确认，并把确认结论写进受理单的「判定依据」栏。
