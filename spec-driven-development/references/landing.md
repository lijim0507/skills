# 落点判定与受理单

## 为什么落点决定一切

文档集是一串上下游依赖：`spec → plan → tasks → 实现`。改动落在链条上的位置，决定了**下游有多少东西可能因此失效**——所以也决定了要从哪重走。

> **位置决定成本。**

## 判定：依次问，第一处「会变」的就是落点

| 依次问 | 会变 → 落点 |
|---|---|
| 验收场景会不会变？ | **spec** |
| 方案会不会变？（引脚 / 外设 / 接口 / 数据模型 / 资源分配） | **plan** |
| 只是既有任务的增删改？ | **tasks** |
| 都不涉及，只是实现修正？ | **仅实现** |

## 为什么锚点是「验收场景」而不是「需求」

「需求会不会变」是个没法直接比对的概念——同一次改动，有人觉得是需求变更，有人觉得只是实现调整。

「**验收场景会不会变**」则可判定：验收场景写在 `01-spec.md` 的用户故事里，格式固定、可观察、可测试，**diff 一下就知道**。

| 例子 | 验收场景 | 落点 |
|---|---|---|
| 引脚 48→47 | US4 验收场景 1/2/3 一个字不变 | **plan** |
| 灭态废除、白=空闲、蓝=测试中 | 验收场景 3「回到 IDLE，白灯常亮」的语义变了 | **spec** |

**额外好处**：验收场景可脚本比对，所以**落点判定可以从「人判断」变成「机器可校验」**——agent 判完落点，脚本还能复核它判得对不对。

## 兜底：判不准按上游

任何一步判不准 → 当成 **spec** 处理。

理由：判错方向的代价**不对称**。

| 误判 | 后果 |
|---|---|
| spec 变更 → 误判成 plan | **一个需求变更未经审批就溜过去了**（失控） |
| plan 变更 → 误判成 spec | 多走一遍全流程（浪费，但不危险） |

## 跨多层取最高

同一次变更同时触到多层时，按**最高**那层处理。

例：面板灯语义重排（spec）+ 脚位 48→47（plan）→ 按 spec 处理，重走范围覆盖到门 1。

## 受理单

判定完落点后，写进 `03-tasks.md` 新增变更轮段的开头：

```markdown
> - **落点**：spec（最高处）｜同时触及 plan（脚位 48→47）
> - **重走范围**：门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge
> - **判定依据**：`01-spec.md` US4 验收场景 3「回到 IDLE，白灯常亮」的语义由「灭态」改为「白常亮」
> - **处置记录**：见 `04-converge.md` 变更轮
```

四栏都不可省：

| 栏 | 为什么必须有 |
|---|---|
| 落点 | 决定重走范围；写出来才能被人审、被脚本校验。**同时触及哪几层也写在这一行**，说明为什么不只重走一处 |
| 重走范围 | **可机器校验**：落点写 spec 却没含门 1 → 矛盾 |
| 判定依据 | 指向具体验收场景，让判定可复核 |
| 处置记录 | 链到 `04-converge.md` 的变更轮，闭合追溯 |

**不要另开「请确认落点」的停顿**：落点决定重走范围，而重走范围的第一站就是一道门——落点是 spec 就过门 1，是 plan 就过门 2，受理单**随第一道门一起受人审**。

## 落点 → 重走范围对照

| 落点 | 重走范围 |
|---|---|
| spec | 门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge |
| plan | 门 2 → tasks → analyze → checklist → implement → converge |
| tasks | checklist → implement → converge |
| 仅实现 | converge |

**为什么 tasks / 仅实现落点无门**：这两类便宜且可逆；而「仅改实现不动文档」本身就是**实现漂移**，会由 `converge` 抓出来。
