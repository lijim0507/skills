# 落点：位置定重走，语义定实质

## 两层，不要混

| 层 | 问什么 | 性质 |
| --- | --- | --- |
| **位置** | 这次改动动了哪份文档？ | **事实**，好核对 |
| **语义** | 这算不算一次需要门的实质修订？ | **判断**，判据是功能等不等价 |

位置决定「从哪道门重走」，语义决定「要不要走门」。两者叠加：

- 动了 `01-spec.md` **且**功能语义变了 → 门 1
- 动了 `01-spec.md` 但功能全量等价（措辞订正）→ **不走门 1**，只在修订记录留一句「语义未变」
- 动了 `02-plan.md` → 门 2
- 只动 `03-tasks.md`（任务 / 任务卡 / 分配说明）→ 任务交接检查 → implement
- 只动代码、文档一字不动 → 让实现对齐已有规范；记一条任务

`01-spec.md` 的「外部契约」节属于产品承诺；改了它按 `01-spec.md` 处理，从门 1 重走。`02-plan-contracts.md` 只写内部契约，改了它按 `02-plan*.md` 处理，从门 2 重走。

## 判不准按上游

任何一步判不准 → 当成**最上游**处理。

| 误判 | 后果 |
| --- | --- |
| 需求变更 → 误判成实现调整 | **需求变更未经审批溜过去了**（失控） |
| 实现调整 → 误判成需求变更 | 多走一遍流程（浪费，但不危险） |

代价不对称，所以兜底一律取上游。

## 跨文档同时改，取最上游

一次改动同时触及 `01` 和 `02`（例如协商后需求从 20 路降到 8 路）→ 按 `01` 处理，重走范围覆盖到门 1。

## 措辞订正的豁免，以及它的边界

改 `01-spec.md` 的措辞而功能全量等价 → 免门 1。这条豁免靠一个**保守近似**兜底：**验收场景段落逐字节未变**。

- 它拦得住明知故犯（改了验收场景却声称是措辞订正）
- 它拦不住换了说法的语义漂移（把「不超过 10 秒」改成「不超过 10 秒左右」）

**这道口子只能靠人守**，别把它当成保证。

外部契约的措辞订正同理；如果消费者、格式、状态码、错误码、SLO 等语义变了，必须走门 1。

## 变更怎么记账

- 每份文档自带「修订记录」节，记：轮次号 / 日期 / 为什么改 / 依据什么 / 谁批的
- 跨文档的一次改动用同一个轮次号串起来
- 门的结论只写一处：**被审的那份文档自己的门小节**（门 1 在 `01-spec.md`，门 2 在 `02-plan.md`）；验收结论落 `04-converge.md`

## 代码改了、文档一字没改

规范驱动的正常路径是「先改文档、后改代码」。有一类改动文档本来就不该动：**实现没做到已有规范**（实现漂移）——该改的是代码，不是文档。

这类靠 `03-tasks.md` 的任务条目留痕：**凡动了代码，至少对应一条任务**。

反过来：**代码和已有 spec 冲突时，不许靠「记一笔」糊过去**——要么改代码对齐规范，要么回门 1 改需求。

## 前提：得拿得到 diff

整套设计依赖能拿到文档改动前后的 diff。所以「先改文档、再改代码」不是礼仪，是这套机制成立的前提——没有文档 diff，落点就推不出来。
