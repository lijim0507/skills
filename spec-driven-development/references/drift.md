# 漂移三分类与处置

> 这是判据的**第二个调用点**（第一个是落点判定）。判据本身与内容归属判据的权威出处：`SKILL.md` 与 `references/doc-set.md`。

## 核心：不是所有漂移都改文档

发现「文档与实现不一致」时，第一反应常是「改规格对齐实现」——**这是错的**。先分类，再动作。

| 类型 | 判据 | 处置 |
|---|---|---|
| **需求漂移** | 用户可观察的行为确实变了（**验收场景变了**） | 改 spec → 走门 1 → 全流程重走 → 重新验收 |
| **实现漂移** | 需求没变，是实现没做到或做成了别的 | 改实现；属范围裁剪则记录后回写 spec |
| **放错位置的漂移** | 漂移的是本该属于 plan 的实现细节 | 搬到正确文档，**spec 不动** |

## 第三类最容易被误判

看到「spec 写 GPIO21、实现是 GPIO19」时，直觉是「改 spec 对齐实现」。

**正确动作：把那行从 spec 删掉，脚位落进 `02-plan.md` 的硬件资源分配表。** spec 那一行本来就不该存在。

第三类之所以容易漏，是因为它**长得像漂移，实质是归属一开始就错了**。反向检验的写法见 `references/doc-set.md`（不在此重复）。

## 这条规则同时保护两样东西

- spec 的变更历史**只反映真实需求变化**
- 门**不会被实现细节的抖动反复触发**

## 一个真实教训

这类不一致（验收场景变了、落点却报成 plan）曾在文件里**躺了近一个月才被发现**——完整经过见 `references/rationale.md`。

它说明的不是判断力问题，而是**受理单没写落点**：没有声明，就没有可核对的东西。所以：

> **变更轮的受理单必须显式写出「落点 + 验收场景 + 重走范围 + 判定依据」。**

前三者可机器校验：`check_intake.py` 查三者自洽，`check_landing.py` 查声明与 `git diff` 是否对得上。**判断是人做的，声明由脚本兜底。**
