# 漂移三分类与处置

## 核心：不是所有漂移都改文档

发现「文档与实现不一致」时，第一反应常是「改规格对齐实现」——**这是错的**。先分类，再动作。

| 类型 | 判据 | 处置 |
|---|---|---|
| **需求漂移** | 用户可观察的行为确实变了（**验收场景变了**） | 改 spec → 走门 1 → 全流程重走 → 重新验收 |
| **实现漂移** | 需求没变，是实现没做到或做成了别的 | 改实现；属范围裁剪则记录后回写 spec |
| **放错位置的漂移** | 漂移的是本该属于 plan 的实现细节 | 搬到正确文档，**spec 不动** |

## 第三类最容易被误判

看到「spec 写 GPIO21、实现是 GPIO19」时，直觉是「改 spec 对齐实现」。

**正确动作：把那行从 spec 删掉，脚位落进 `02-plan.md` 的硬件资源分配表。** spec 那一行本来就不该存在。

第三类之所以容易漏，是因为它**长得像漂移，实质是归属一开始就错了**。

**反向检验**：spec 里出现 `GPIO21`、`TMR3 CH2`、`uint8_t` 这类符号时，问一句「删掉它，验收还做得成吗？」——做得成 → 它只是实现注脚，搬去 plan；做不成（如成功标准「抓 GPIO 波形验证」是验收手段）→ 可以留。

## 这条规则同时保护两样东西

- spec 的变更历史**只反映真实需求变化**
- 评审门**不会被实现细节的抖动反复触发**

## 一个真实教训

某变更轮的记录把它分类成「需求漂移」、改了 spec 的成功标准，但门走的是门 2。

按规则，验收场景变了就是 spec 落点，应该走门 1。**这个不一致在文件里躺了近一个月，直到逐行对账才发现。**

所以新增一条纪律：

> **变更轮的受理单必须显式写出「落点 + 依据 + 重走范围」。**

三者可机器校验（落点写 spec，重走范围却没含门 1 → 报错）。**判断是人做的，自洽性由脚本兜底。**
