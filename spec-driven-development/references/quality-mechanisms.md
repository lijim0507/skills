# 关卡：人审门与机器守卫

> 流程模型的权威出处是 `SKILL.md`。本文件解释关卡的判法、写权限与终止条件，不复述落点表与重走范围表。

## 完整状态图

```text
S0 建项（还没有文档集）
  ↓ 提取宪法 → 用户 ratify → 写 spec
S1 spec 待审 ──门 1（人，阻塞点）── approve → S2 ／ reject → 回 S1 修
  ↓
S2 plan 待审 ──门 2（人，阻塞点）── approve → S3 ／ reject → 回 S2 修
  ↓
S3 tasks 待审 ──analyze（只写自己那一节）── 未闭合项 0 → S4 ／ 有 → 回上游修
  ↓
S4 待实现 ──checklist（评审者已勾）── 全勾 → S5 ／ 有未勾 → 停下问
  ↓
S5 实现中 ──全部 [x] / [~]──→ S6
  ↓
S6 收敛 ──converge（只追加）── Converged → S7 ／ Tasks appended → 回 S5
  ↓
S7 完成
```

`SKILL.md` 的「重走顺序」是这张图的压缩版。

## 两类关卡，别混

表格见 `SKILL.md` 的「两类关卡」，本文件不复述。要记住的是两条差异：人审门的**通过标准是人的判断**，所以它拦不住「判断错」，只拦得住「没批就往下走」；机器守卫的**通过标准是确定的检查项**，所以它对没写进检查项的问题视而不见，别指望它兜住你没想到的风险。

## 门的规则

### 门是阻塞点

**写完 spec / plan 必须停下**，把文档与受理单交给用户审批，拿到明确 approve 才能进入下一步。**不得自行填写 approve**，也不得在未获批时继续往下走。

这不是形式主义——门是这条流程里唯一由人保留的否决权。

### 首轮：全量审

从无到有，所以全部内容都要过。

### 变更轮：只审变动部分

**没动过的部分沿用上次的结论，不重审。**

所以「门 2 复审**维持** approve」不是橡皮图章，它的准确含义是：**没变的部分保持原结论，变了的部分重新审**。门只有一道，变的是**审查范围随 diff 收缩**。

### reject 之后

**reject → 退回该门的上游修 → 修完重跑该门**

- 门 1 reject → 回 `01-spec.md` 修
- 门 2 reject → 回 `02-plan*.md` 修

`on_reject: abort` 里的 **abort 不是「放弃这个需求」，是「不进入下一步」**。**不得带病继续。** 经验：当同一批问题在门、清单两处同时冒头时，说明不修就会一直漏。

### 门的退出证据与记录位置

一条规则，两处落点：

| 情形   | 结论写在哪                                                             | 要求                                                                           |
| ------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 首轮   | 被审文档的门小节（门 1 在`01-spec.md`、门 2 在 `02-plan.md`）      | 清单全勾 + 结论行 = approve + 裁决人 + 日期                                    |
| 变更轮 | 受理单（`03-tasks.md` 的变更轮段）——受理单就是这个变更轮的人审材料 | 重走范围里经过的门各一条：> -**门 N**：approve ｜ 裁决人：… ｜ 日期：… |

清单与结论行**只由评审者写**（见 `SKILL.md` 的写权限与证据表）。
`check_gate.py` 校验这件事：经过的门必须有对应记录、必须 `approve`、必须带裁决人与日期——`待审`、`reject`、占位符（`<…>`）都报错。**它抓不出「谁签的字」**：裁决人一栏填的是不是真人，只有人自己守得住。所以 `SKILL.md` 规定「未获用户明确批准时一律写 `待审`」，而不是假装脚本能识破自批。

## 机器守卫

### `analyze` —— 文档间一致性（实现前）

对 `spec` / `plan` / `tasks` 做跨产物一致性分析，报告冲突、缺口与歧义（如某任务没有对应需求、某方案选择与规格矛盾）。

- **唯一的写权限**：`03-tasks.md` 的「analyze 交叉检查」一节。**不改需求、方案、任务内容**——「只读」的确切含义是「不修改被检查的内容」，而不是「不写任何文件」
- 发现问题**回上游修**：需求问题回 spec，设计问题回 plan，任务问题回 tasks
- 修完**重跑 `analyze` 直至干净**（该节未闭合项 = 0）

### `converge` —— 实现 vs 文档（实现后）

对照 spec / plan / tasks 评估**实现**，确认没有遗漏。

- **只追加**：从不编辑或删除代码或文档正文；唯一写入是往 `03-tasks.md` 追加任务
- **只在当前 `tasks.md` 上的 implement 跑过之后才可运行**
- 结果二选一：
  - **Converged** —— 无缺口。判据：除本次追加外，`tasks.md` **逐字节不变**
  - **Tasks appended** —— 有缺口，追加到 `03-tasks.md` 的 Convergence 段 → 再 `implement` → 再 `converge`

### `checklist` —— 门 1 的清单，不是第四道机制

需求质量清单（「给需求写的单元测试」，**不测试代码**）就在 `01-spec.md` 的门 1 里，**由评审者勾选**：`[x]` 表示评审者认定需求质量达标，**不代表实现工作已完成**。

重走范围里的 `checklist` 这一站，指的是 `implement` 前对它的**只读复核**：只能统计已勾 / 未勾，发现有未勾就**停下询问**，不得自己打勾。

```text
Checklist（01-spec.md 门 1）      Total  Checked  Unchecked  Status
需求质量清单                       5      4        1          FAIL
```

### 终止条件

> **每轮发现数必须严格递减。某轮不降反增 → 立即停下回上游。**

理由：发现数反弹说明**在打转**，而打转通常不是实现的问题，是 **spec / plan 本身有问题**——实现怎么改都追不上一个自相矛盾或有洞的规格。这时候继续跑 `implement → converge` 只会烧钱。

## 为什么它们都禁止「就地改到通过」

`checklist` 不许自己打勾、`analyze` 只写自己的报告节、`converge` 只追加——共同点是**问题必须回到拥有它的地方解决**。

这条把「是否真的收敛」变成了**可信任的结论**：工具不会为了让检查通过而偷偷改东西。发现问题时它唯一能做的就是**把问题变成新任务交给人**。

## 变更轮要跑哪几道

**重走路径上经过的检查，全部照跑**——人批的门和自动的质量机制一视同仁，不需要另立规则。

推论：spec 落点和 plan 落点的重走路径都会穿过 `analyze`，所以**变更轮也要跑 analyze**。

> 常见漏检：变更轮只跑了 `converge` 就收工。但 `converge` 只查「实现有没有背叛文档」，查不出「**文档内部自相矛盾**」——那是 `analyze` 的活。

> 唯一的例外是落点 `澄清`（改的只是 spec 措辞、验收场景不变）：重走 `门 1 → analyze` 即可，不跑 `converge`——没有实现改动，收敛检查无从谈起。
