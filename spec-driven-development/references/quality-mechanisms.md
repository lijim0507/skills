# 门与三道质量机制

## 两种东西，别混

| | 门（评审门 1 / 2） | 三道质量机制 |
|---|---|---|
| 谁来判 | **人** approve / reject | **脚本或 agent** |
| 通过标准 | 人的判断 | 确定的检查项 |
| 失败时 | reject → 退回上游修 | 见下 |

## 门的规则

### 首轮：全量审

从无到有，所以全部内容都要过。

### 变更轮：只审变动部分

**没动过的部分沿用上次的结论，不重审。**

所以「评审门 2 复审**维持** approve」不是橡皮图章，它的准确含义是：**没变的部分保持原结论，变了的部分重新审**。门只有一道，变的是**审查范围随 diff 收缩**。

### reject 之后

`on_reject: abort` 的 **abort 不是「放弃这个需求」，是「不进入下一步」**：

> **reject → 退回该门的上游修 → 修完重跑该门**

- 门 1 reject → 回 `01-spec.md` 修
- 门 2 reject → 回 `02-plan*.md` 修

**不得带病继续。** 经验：当同一批问题在门、清单两处同时冒头时，说明不修就会一直漏。

## 三道质量机制

### `checklist` —— 需求质量清单

检查**规格本身**是否完整、清晰、无歧义、自洽——可以理解成「给需求写的单元测试」。**不测试代码。**

- **归评审者所有**：`[x]` 表示评审者认定需求质量达标，**不代表实现工作已完成**
- `implement` 对它**只读**：只能统计已勾/未勾，发现有未勾就**停下来问**，不得自己打勾

```text
| Checklist               | Total | Checked | Unchecked | Status  |
|-------------------------|-------|---------|-----------|---------|
| requirements-quality.md | 7     | 4       | 3         | FAIL    |
```

### `analyze` —— 文档间一致性（实现前）

对 `spec` / `plan` / `tasks` 做**只读**的跨产物一致性分析，报告冲突、缺口与歧义（如某任务没有对应需求、某方案选择与规格矛盾）。

- **从不修改文件**——它产出报告
- 发现问题**回上游修**：需求问题回 spec，设计问题回 plan，任务问题回 tasks
- 修完**重跑 `analyze` 直至干净**

### `converge` —— 实现 vs 文档（实现后）

对照 spec / plan / tasks 评估**实现**，确认没有遗漏。

- **只追加**：从不编辑或删除代码；唯一写入是往 `tasks.md` 追加任务
- **只在当前 `tasks.md` 上的 implement 跑过之后才可运行**
- 结果二选一：
  - **Converged** —— 无缺口。判据：`tasks.md` **逐字节不变**
  - **Tasks appended** —— 有缺口，追加到 `tasks.md` 的 Convergence 段 → 再 `implement` → 再 `converge`

### 终止条件

> **每轮发现数必须严格递减。某轮不降反增 → 立即停下回上游。**

理由：发现数反弹说明**在打转**，而打转通常不是实现的问题，是 **spec/plan 本身有问题**——实现怎么改都追不上一个自相矛盾或有洞的规格。这时候继续跑 `implement → converge` 只会烧钱。

## 为什么三者都禁止「就地改到通过」

`checklist` 不许自己打勾、`analyze` 只读、`converge` 只追加——共同点是**问题必须回到拥有它的地方解决**。

这条把「是否真的收敛」变成了**可信任的结论**：工具不会为了让检查通过而偷偷改东西。发现问题时它唯一能做的就是**把问题变成新任务交给人**。

## 变更轮要跑哪几道

**重走路径上经过的检查，全部照跑**——人批的门和自动的质量机制一视同仁，不需要另立规则。

推论：spec 落点和 plan 落点的重走路径都会穿过 `analyze`，所以**变更轮也要跑 analyze**。

> 常见漏检：变更轮只跑了 `converge` 就收工。但 `converge` 只查「实现有没有背叛文档」，查不出「**文档内部自相矛盾**」——那是 `analyze` 的活。
