# 设计说明：为什么是这三条内核

> **这份文件是给人读的**（维护者、评审人、接手的人）。agent 执行流程只需要 `SKILL.md`；这里记的是「为什么这么设计」和踩过的坑。
> **规则本身的权威出处仍是 `SKILL.md` 的「流程模型（唯一权威）」**——本文件不定义任何规则，也不复述那些表。

## 起因：软件变更失控只有三种形态

| 形态                   | 表现                                 | 后果               |
| ---------------------- | ------------------------------------ | ------------------ |
| 需求变更未经审批溜进去 | 实现改着改着，行为和当初定好的不一样 | 失控               |
| 实现偷偷偏离文档       | 代码改了，文档还是旧的               | 文档失效、评审失效 |
| 文档内部自相矛盾       | tasks 还写着已经废除的旧方案         | 实现永远追不上规格 |

三种形态有一个共同点：**失败没有本地信号**。没人会在需求绕过门 1 的那一刻告诉你，往往是几周后逐行对账才发现。所以约束不能靠「提醒模型注意」，只能靠**可核对的声明 + 机械检查**。

## 于是只需要三样东西

- **一个判据**：改它，验收场景变没变？——「需求会不会变」无法直接比对，「验收场景」可观察、可 diff，所以既能由人判断，也能由脚本兜底。
- **一条链**：`spec → plan → tasks → 实现`。文档集是上下游依赖，改动落点决定下游有多少东西失效，所以决定从哪重走——**位置决定成本**。
- **一份证据**：每个「完成 / 通过」都要挂可核对的证据；谁写什么由写权限划定。

其余全是推论：落点表、重走范围、状态机、两类关卡、受理单、5 个校验脚本、文档集与模板。**看到一条规则时，先问它是从哪条内核推出来的**；推不出来的，很可能是补丁。

## 为什么锚点是「验收场景」而不是「需求」

「需求会不会变」没法直接比对——同一次改动，有人觉得是需求变更，有人觉得只是实现调整。而「**验收场景会不会变**」可判定：它写在 `01-spec.md` 的用户故事里，格式固定、可观察、可测试，diff 一下就知道。

| 例子                         | 验收场景                      | 落点 |
| ---------------------------- | ----------------------------- | ---- |
| 引脚 48→47                  | US4 验收场景 1/2/3 一个字不变 | plan |
| 灭态废除、白=空闲、蓝=测试中 | 验收场景 3 的语义变了         | spec |

## 为什么判不准要按上游

判错方向的代价**不对称**：

| 误判                     | 后果                                     |
| ------------------------ | ---------------------------------------- |
| spec 变更 → 误判成 plan | **需求变更未经审批溜过去**（失控） |
| plan 变更 → 误判成 spec | 多走一遍全流程（浪费，但不危险）         |

所以兜底一律取上游；并且这条判断要写进受理单，因为它**可以被脚本证伪**。

## 为什么 tasks / 仅实现落点无门

这两类改动便宜且可逆；而「仅改实现不动文档」本身就是实现漂移，会由 `converge` 抓出来。给它们加门只会促使人绕过门。

## 为什么还要有「澄清」这一档

落点表是穷举式的：依次问下去，「把 spec 里的错别字改掉」会连着答四个「不」，最后落进「仅实现」——重走范围只剩 `converge`，等于把一次文字订正送去和实现比对。补上「澄清」（改 spec 措辞、验收场景不变 → 门 1 → analyze）后，既不必为错别字走 plan 与门 2，也不会把它错当成实现修正；而 `check_landing.py` 仍会在「其实是语义变更」时报错。

## 为什么门结论的落点只有两处

首轮的门审的就是那份文档（门 1 → `01-spec.md`、门 2 → `02-plan.md`），结论写在该文档的门小节里最不容易脱节。变更轮没有独立的文档副本，**受理单就是它的人审材料**，所以结论写在受理单里。

`check_gate.py` 两处都查：必须 `approve`，且带裁决人与日期——`待审`、`reject`、占位符都过不去。它拦得住「忘了批」，拦不住「谁批的」：署名的真实性只有人守得住，所以规则写成「未获用户明确批准时一律填 `待审`」，而不是假装脚本能识破自批。

## 为什么写权限这样划

`checklist` 不许自己打勾、`analyze` 只写自己那一节、`converge` 只追加——共同点是**问题必须回到拥有它的地方解决**。

这样「是否真的收敛」才是可信任的结论：工具不会为了让检查通过而偷偷改东西；发现问题时它唯一能做的是**把问题变成新任务交给人**。

## 判决由人做，声明由脚本兜底

| 脚本                 | 保证什么                                                     |
| -------------------- | ------------------------------------------------------------ |
| `check_spec.py`    | 规格结构完整（章节、每个故事的验收场景、SC、无实现细节泄漏） |
| `check_intake.py`  | 受理单自洽：落点 ↔ 重走范围 ↔ 验收场景                     |
| `check_tasks.py`   | 任务状态与作废格式（含任务号不被划进删除线）                 |
| `check_gate.py`    | 门留下了「人批准」的记录                                     |
| `check_landing.py` | 受理单的声明与真实`git diff` 对得上                        |

**没有哪个脚本判断「落点判得对不对」**——那是人的判断。脚本只保证两件事：声明之间不打架、声明与事实不打架。

## 两次真实事故

### 1. 需求变更绕过门 1，躺了近一个月

某变更轮被分类成「需求漂移」、改了 spec 的成功标准，但门走的是**门 2**。一个未经门 1 的需求变更就这么溜过去了，直到逐行对账才发现。

成因不是判断力不够，而是**受理单没写落点**——没有声明，就没有可核对的东西。所以后来加了三个字段（落点 / 验收场景 / 重走范围）与两个脚本。

### 2. 引脚号漂移，逼着走规格变更

工装项目里按键脚从 IO21 改到 IO19 又改回 IO21，SWD 脚也调整过一轮，而「按下按键开始测试」这条需求从头到尾一个字没改。

脚位写进 spec 的代价是：**每次纯实现调整都要走一遍规格变更 + 门 1 + 重新验收，为一次实现调整付三倍成本**；同时 spec 的 diff 被实现细节淹没，评审「需求到底变没变」时全是噪声。

## 为什么这个 skill 比别人长

别人的 skill 通常约束**一个动作**（抽 PDF、转格式）。那个动作对不对，看一眼结果就知道，所以一段提示词就够。

这里约束的是**一条跨多轮、跨人员的流程**，它的失败没有本地信号，只能靠制度与证据：模板（产物形状）、门禁（人的否决权）、脚本（机械兜底）、回归用例（改 skill 时的保险丝）。**长度来自这里，不来自修辞。**

人读的部分（就是本文件）被刻意从 `SKILL.md` 里搬出来：`SKILL.md` 只留 agent 要执行的东西，约占整个 skill 的 11%，其余按需载入。
