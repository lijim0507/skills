# 文档集、职责边界与内容归属判据

## 一套文档，长期存活

项目建项时讨论确定一套文档，之后**所有变更都在这一套上改和记录**——不新建文档集，不为单次变更开新目录。

变更的记录形式是**变更轮**（`r2`、`r3`…），落在 `03-tasks.md` 的变更轮段，以及 `04-converge.md` 的处置记录里。

## 内容归属判据（本文件是这条判据的权威出处）

`SKILL.md` 的判据用在「写文档」这个时机上，就是下面这一问：

> **删除这段内容，验收还做得成吗？**
> 做得成 → 它是实现注脚，属于 `02-plan.md`（或更细的 Phase 1 产物）；
> 做不成 → 它属于 `01-spec.md`。

| 内容类型                                                 | 归属                                       | 为什么                                                                           |
| -------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------- |
| 用户可观察的行为、验收基准                               | `01-spec.md`                             | 删了它验收做不成                                                                 |
| **引脚号、外设通道、时钟树、中断优先级、DMA 通道** | `02-plan.md` 硬件资源分配表              | 删了它需求一字不动——纯实现约束                                                 |
| 「怎么触发与观察」的验证手段（接线、命令、工具）         | `02-plan.md` 验证手段表                  | 它是证明需求成立的手段，本身不是需求                                             |
| 函数签名、协议帧格式、错误码                             | `02-plan-contracts.md`                   | 模块间的软件接口                                                                 |
| 结构体、字段、状态迁移                                   | `02-plan-data-model.md`                  | 内存里的形状                                                                     |
| 「引脚宏必须收敛到唯一头文件」这类**纪律**         | `00-constitution.md`                     | 管辖所有方案的规则，本身不含具体值                                               |
| 外部给定、不可协商的硬约束                               | `01-spec.md`，但写成「约束」而非「设计」 | 它不是选择，是前提；写进「前提假设」节，`check_spec.py` 不对该节报实现细节警告 |

### 为什么引脚号尤其不能进 spec

引脚天然会漂移。真实案例：工装项目里按键脚从 IO21 改到 IO19 又改回 IO21，SWD 脚也调整过一轮，而「按下按键开始测试」这条需求从头到尾一个字没改。

脚位写进 spec 的代价是——**每次实现调整都要走一遍规格变更 + 门 1 + 重新验收，为一次纯实现调整付三倍成本**；同时 spec 的 diff 被实现细节淹没，评审「需求到底变没变」时全是噪声。

**反向检验**（`references/drift.md` 引用本处）：spec 里出现 `GPIO21`、`TMR3 CH2`、`uint8_t`、`PA5`、`I2C1`、`DMA 通道`、`中断优先级` 这类符号时，先问一句「删掉它，验收还做得成吗？」——做得成，说明它只是实现注脚，该搬去 plan；做不成（例如成功标准「抓 GPIO 波形验证」本身就是验收手段），才可以留。

`check_spec.py` 会把这类符号报成警告。四类行除外：`- [ ]` 清单行、`>` 注记行（它们本来就在讲这件事）、**「前提假设」节内的行**（外部给定的硬约束允许含具体值）、以及带 `<!-- impl-ok -->` 标记的行。门 1 的清单里因此挂了一条「无实现细节警告」。

| 文件                      | 写什么                                                                                                  | 不写什么               | 谁写 / 下游消费者                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------- |

| `02-plan.md`            | 技术上下文、硬件资源分配、验证手段、宪法检查、复杂度跟踪、待办与偏差登记、门 2 清单与结论               | 需求（不重复 spec）    | 评审者写门 2 结论；消费者：门 2、各 Phase 1 子件            |

> **每份文档都必须有消费者或检查机制；没有的，删掉。**（2.0.0 删掉 `02-plan-quickstart.md` 就是这条规则的执行。）

## 编号纪律

- **FR 编号不重用**：裁掉的 FR 保留编号、原地标 `Deferred` / `Cut`（写法见 `01-spec.md` 模板）；将来恢复用原编号
- **任务编号单调递增**：`T001` 起顺序编号；`converge` 追加的任务用独立段号（如 `T9xx`），与首轮编号不混
- **两套发现编号不混**：`analyze` 的发现编号与 `converge` 的发现编号是两套，引用时必须带小节名
