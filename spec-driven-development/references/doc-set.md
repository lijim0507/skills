# 文档集：每份文档写什么、谁写、谁消费

## 一套文档，长期存活

项目建项时落一套，之后所有改动都在**同一套**上改和记录——不新开文档集，不为单次改动开新目录。历史由各文档自带的「修订记录」节 + git 承担。

## 三顶帽子与三份主文档

| 帽子 | 主文档 | 只回答 | 交接给谁 |
| --- | --- | --- | --- |
| 产品经理 | `01-spec.md` | 谁在什么场景下遇到什么问题，什么算做对了？ | 技术总监 |
| 技术总监 | `02-plan*.md` | 在现有约束下怎么做，为什么这样最合适？ | 任务负责人 |
| 任务负责人 | `03-tasks.md` | 谁在什么边界内做什么，怎么算完成？ | 实现者 |

产品不写方案，技术不改需求，任务不重新设计架构。三份文档的边界就是三顶帽子的边界。

## 内容归属判据

写文档时唯一要问的问题：

> **这段内容，约束的是外部消费者可观察、可依赖的承诺，还是内部的实现自由度？**

- 约束**外部消费者可观察、可依赖的承诺** → `01-spec.md`
- 约束**内部的实现自由度** → `02-plan.md` 或它的 Phase 1 子件

**判据不是「是不是数字」。** 这是最容易搞错的一处：

| 内容 | 归属 | 为什么 |
| --- | --- | --- |
| 「内部缓存用 Redis」 | plan | 外部看不见，内部选择 |
| 「亮度分 8 档」 | spec | 用户数得出来——它约束可观察行为 |
| 「`POST /orders` 返回 `201`，重复提交返回 `409`」 | spec（外部契约） | 外部消费者直接依赖 |
| 「订单表按 `user_id` 分库」 | plan | 外部看不见，内部实现 |
| 「P95 延迟 < 300ms」 | spec（质量承诺） | 外部可度量、可验收 |
| 「数据库连接池 = 20」 | plan | 内部调参 |
| 「外部依赖必须通过统一适配层访问」 | 00-constitution | 管辖所有方案的纪律，本身不含具体值 |
| 「超时后返回错误码」 | spec（行为）+ plan（超时值） | 行为是需求，具体毫秒数是实现 |

协商的结果常常是个数字（20 路做不了、只能 8 路），**这个数字进 spec 是对的**——它已经变成对用户的承诺，不是技术细节。

外部契约写在 `01-spec.md` 的「外部契约」节，不新增文件。`02-plan-contracts.md` 只写产品边界内部的契约；如果契约会被外部消费者依赖，它属于 `01-spec.md`。

## 各文档一览

| 文件 | 写什么 | 不写什么 | 谁写 / 谁消费 |
| --- | --- | --- | --- |
| `00-constitution.md` | 可判定的原则：编号 + 注明出处 | 具体实现值（内部标识、私有参数等） | 人；消费者：`02-plan.md` 的宪法检查 |
| `01-spec.md` | 产品根（消费者 + 问题 + 使用价值 + 场景 + 现有替代 + 成功信号）、用户故事（场景与结果 + 解决方向）、FR、验收、成功标准、外部契约；结构与写法见 `examples/todo-cli/SDD/01-spec.md` | 任何内部实现手段 | 产品经理写；裁决人写门1结论；消费者：门1、`02` 的可行性核对、`03` 的覆盖映射、契约测试 |
| `02-plan.md` | 方案总览、需求可行性核对、技术上下文、模块划分、数据与契约、质量属性、关键决策与备选、风险与应对、交付/迁移/回滚、验证手段、宪法检查、复杂度跟踪、门2清单与结论、交接给任务拆解、修订记录 | 需求与外部契约（不重复 spec） | 技术总监写；裁决人写门2结论；消费者：门2、Phase 1 子件、任务拆解 |
| `02-plan-research.md` | Phase 0：每个决策 + 被否决的方案 + 验证方式 | — | `02-plan.md` |
| `02-plan-data-model.md` | Phase 1：实体、字段、状态迁移、归属与写权限 | — | contracts、任务拆解 |
| `02-plan-contracts.md` | Phase 1：模块清单、依赖方向、模块间契约（产品边界内） | 外部契约 | 各模块实现；门2；analyze 检查它与 spec / plan 是否自洽 |
| `03-tasks.md` | 任务分配说明、执行批次、任务、任务卡、覆盖映射、analyze 交叉检查、开工前检查、收敛追加段、修订记录 | 实现细节、重新论证架构 | 任务负责人写；消费者：implement、converge |
| `04-converge.md` | 本轮收敛结论：发现了什么、怎么处置、结论、验收证据 | 历史流水账 | 验收（S8 的退出证据） |

`02-plan-contracts.md` 的前置是 `02-plan.md` 的「模块划分」；它消费 `02-plan-data-model.md` 的实体，不消费分层类别或泛指角色。

## 交接摘要不是文档摘要

每份主文档末尾的「交接给…」只写下一顶帽子必须知道、但正文和 diff 里看不出来的判断：取舍、边界、风险、什么不能动。不要把正文再抄一遍。模板见 `references/handoffs.md`。

## 任务卡是工单，不是索引

`03-tasks.md` 的索引行（`- [ ] T001 …`）用于扫描、统计和脚本检查；**执行者实际使用的是任务卡**。非平凡任务必须有卡，卡里写清目标、范围、输入、产出、DoD、验证、依赖和回滚。只有简单任务（如改文案）可以只用索引行。

## 每条原则都必须有落点

`00` 里每一条原则的落点，由它管什么决定：

- 管**行为/外部承诺**的原则 → 落到 `01-spec.md`，变成验收场景、FR 或外部契约项
  （例：`C-02 对外接口必须可超时` → 每个涉及通信的故事都要有「超时 → 返回错误码」的验收场景或外部契约项）
- 管**做法**的原则 → 落到 `02-plan.md`，变成宪法检查的一项
  （例：`C-01 外部依赖必须通过统一适配层访问`）

**推论：一条原则如果既没在 `01` 里露面、也没在 `02` 里被检查，它就是死原则**——该删，或者该承认它只是个人偏好，不够格进宪法。

## 编号纪律

- **FR / SC 编号不重用**：裁掉的需求保留编号，原地标 `Deferred`（延期）或 `Cut`（不做），写明理由 + 裁决人 + 日期；恢复时用回原编号
- **任务编号单调递增**：`T001` 起顺序编号，不复用
- **收敛追加的任务**接在末尾的「收敛追加」段，继续往后编号，不与首轮混段
- **轮次号**：一次改动跨多份文档时，用同一个 `r2` / `r3` 串起来

## 修订记录只写 diff 看不到的

改了什么，diff 里有。修订记录写**为什么改、依据什么、谁批的、这一轮到哪为止**。否则每条记录都会退化成「r2：调整实现」这种零信息量的废话。

## 每份文档都必须有消费者

没有消费者、也没有检查机制的文档，删掉。
