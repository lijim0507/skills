# 文档集与职责边界

## 一套文档，长期存活

项目建项时讨论确定一套文档，之后**所有变更都在这一套上改和记录**——不新建文档集，不为单次变更开新目录。

变更的记录形式是**变更轮**（`r2`、`r3`…），落在 `03-tasks.md` 的任务段，以及 `04-converge.md` 的处置记录里。

## 职责边界（最要紧的一节）

官方只说「spec 写 what/why、plan 是实现细节该出现的地方」，但没说边界怎么切。实践里反复咬人的是这个问题：**引脚号、外设通道、时钟配置、结构体字段，到底写在哪？**

一条判据就够用：

> **把这段内容改掉，需求会跟着变吗？**
> 会变 → `01-spec.md`；不变 → `02-plan.md`（或更细的 Phase 1 产物）。

| 内容类型 | 归属 | 为什么 |
|---|---|---|
| 用户可观察的行为、验收基准 | `01-spec.md` | 改了它，需求就变了 |
| **引脚号、外设通道、时钟树、中断优先级、DMA 通道** | `02-plan.md` 硬件资源分配表 | 改了它，需求一字不动——纯实现约束 |
| 函数签名、协议帧格式、错误码 | `02-plan-contracts.md` | 模块间的软件接口 |
| 结构体、字段、状态迁移 | `02-plan-data-model.md` | 内存里的形状 |
| 「引脚宏必须收敛到唯一头文件」这类**纪律** | `00-constitution.md` | 管辖所有方案的规则，本身不含具体值 |
| 外部给定、不可协商的硬约束 | `01-spec.md`，但写成「约束」而非「设计」 | 它不是选择，是前提 |

### 为什么引脚号尤其不能进 spec

引脚天然会漂移。真实案例：工装项目里按键脚从 IO21 改到 IO19 又改回 IO21，SWD 脚也调整过一轮，而「按下按键开始测试」这条需求从头到尾一个字没改。

脚位写进 spec 的代价是——**每次实现调整都要走一遍规格变更 + 评审门 + 重新验收，为一次纯实现调整付三倍成本**；同时 spec 的 diff 被实现细节淹没，评审「需求到底变没变」时全是噪声。

**反向检验**：spec 里出现 `GPIO21`、`TMR3 CH2`、`uint8_t` 这类符号时，先问一句「删掉它，验收还做得成吗？」——做得成，说明它只是实现注脚，该搬去 plan；做不成（例如成功标准「抓 GPIO 波形验证」是验收手段），才可以留。

## 编号纪律

- **FR 编号不重用**：裁掉的 FR 保留编号、原地标 `Deferred`/`Cut`；将来恢复用原编号
- **任务编号单调递增**：`T001` 起顺序编号；`converge` 追加的任务用独立段号（如 `T9xx`），与首轮编号不混
- **两套发现编号不混**：`analyze` 的发现编号与 `converge` 的发现编号是两套，引用时必须带小节名
