# 文档集：每份文档写什么、谁写、谁消费

## 一套文档，长期存活

项目建项时落一套，之后所有改动都在**同一套**上改和记录——不新开文档集，不为单次改动开新目录。历史由各文档自带的「修订记录」节 + git 承担。

## 内容归属判据

写文档时唯一要问的问题：

> **这段内容，约束的是用户可观察的行为，还是内部的实现自由度？**

- 约束**用户可观察的行为** → `01-spec.md`
- 约束**内部的实现自由度** → `02-plan.md` 或它的 Phase 1 子件

**判据不是「是不是数字」。** 这是最容易搞错的一处：

| 内容 | 归属 | 为什么 |
| --- | --- | --- |
| `PWM 输出 = PA5` | plan | 用户看不见，内部选择 |
| 「亮度分 8 档」 | spec | 用户数得出来——它约束可观察行为 |
| 「引脚宏收敛到唯一头文件」 | 00-constitution | 管辖所有方案的纪律，本身不含具体值 |
| 「超时后返回错误码」 | spec（行为）+ plan（超时值） | 行为是需求，具体毫秒数是实现 |

协商的结果常常是个数字（20 路做不了、只能 8 路），**这个数字进 spec 是对的**——它已经变成对用户的承诺，不是技术细节。

## 各文档一览

| 文件 | 写什么 | 不写什么 | 谁写 / 谁消费 |
| --- | --- | --- | --- |
| `00-constitution.md` | 可判定的原则：编号 + 注明出处 | 具体值（引脚号、参数） | 人；消费者：`02-plan.md` 的宪法检查 |
| `01-spec.md` | 用户故事与验收场景、FR、SC、假设与未决项、门1清单与结论、修订记录 | 任何实现手段 | 裁决人写门1结论；消费者：门1、`03-tasks.md` 的覆盖映射 |
| `02-plan.md` | 技术上下文、硬件资源分配、验证手段、宪法检查、复杂度跟踪、门2清单与结论、修订记录 | 需求（不重复 spec） | 裁决人写门2结论；消费者：门2、Phase 1 子件 |
| `02-plan-research.md` | Phase 0：每个决策 **+ 被否决的方案** | — | `02-plan.md` |
| `02-plan-data-model.md` | Phase 1：实体、字段、状态迁移 | — | contracts |
| `02-plan-contracts.md` | Phase 1：接口契约（按执行上下文分层） | — | 各模块实现；analyze 检查它与 spec / plan 是否自洽 |
| `03-tasks.md` | 任务、依赖、覆盖映射、analyze 交叉检查、开工前检查、收敛追加段、修订记录 | 实现细节 | implement、converge |
| `04-converge.md` | 本轮收敛结论：发现了什么、怎么处置、结论 | 历史流水账 | 验收（S8 的退出证据） |

## 每条原则都必须有落点

`00` 里每一条原则的落点，由它管什么决定：

- 管**行为**的原则 → 落到 `01-spec.md`，变成验收场景或 FR
  （例：`C-02 对外接口必须可超时` → 每个涉及通信的故事都要有「超时 → 返回错误码」的验收场景）
- 管**做法**的原则 → 落到 `02-plan.md`，变成宪法检查的一项
  （例：`C-01 引脚宏必须收敛到唯一头文件`）

**推论：一条原则如果既没在 `01` 里露面、也没在 `02` 里被检查，它就是死原则**——该删，或者该承认它只是个人偏好，不够格进宪法。

## 编号纪律

- **FR / SC 编号不重用**：裁掉的需求保留编号，原地标 `Deferred`（延期）或 `Cut`（不做），写明理由 + 裁决人 + 日期；恢复时用回原编号
- **任务编号单调递增**：`T001` 起顺序编号，不复用
- **收敛追加的任务**接在末尾的「收敛追加」段，继续往后编号，不与首轮混段
- **轮次号**：一次改动跨多份文档时，用同一个 `r2` / `r3` 串起来

## 修订记录只写 diff 看不到的

改了什么，diff 里有。修订记录写**为什么改、依据什么、谁批的、这一轮到哪为止**。否则每条记录都会退化成「r2：调整引脚」这种零信息量的废话。

## 每份文档都必须有消费者

没有消费者、也没有检查机制的文档，删掉。
