# 测试用例

约定：退出码 0 = 无「错误」（警告与提示不阻断）；退出码 1 = 有「错误」。
围栏（三连反引号）内的内容一律被跳过。

## check_spec.py

### 用例 1：完整规格通过
- 输入：含「用户场景与测试 / 需求 / 成功标准」，2 个用户故事各带验收场景，有 SC-001
- 期望：输出 `规格校验通过`，退出码 0

### 用例 2：章节名容错
- 输入：章节写成 `## 功能需求`、`## 成功标准`
- 期望：退出码 0（旧版会误报「缺少必需章节」）

### 用例 3：缺章节
- 输入：缺「成功标准」
- 期望：报 `错误：缺少必需章节「成功标准」`，退出码 1

### 用例 4：用户故事缺验收场景
- 输入：2 个用户故事只有 1 个 `**验收场景**`
- 期望：报错并提示「验收场景是判据的锚点」，退出码 1

### 用例 5：实现细节泄漏（两类符号都要抓）
- 输入：正文出现 `GPIO21`、`uint8_t`；另一份出现 `PA5`、`I2C1`、`DMA`、`中断优先级`
- 期望：都报 `警告：spec 里出现实现细节`，退出码 0（警告不阻断）

### 用例 6：清单行与注记行不算泄漏
- 输入：门 1 清单行、`>` 注记行里提到引脚号（它们本来就在讲这条判据）
- 期望：不报泄漏

### 用例 7：门 1 缺结论
- 输入：有门 1 小节但没有 `**结论**` 行
- 期望：报 `警告：门 1 小节缺少「结论」行`，退出码 0

### 用例 7a：验收场景写错故事也不放过
- 输入：2 个用户故事，2 个 `**验收场景**` 块全写在故事 1 名下，故事 2 一个都没有
- 期望：报 `这些用户故事名下没有「验收场景」`，退出码 1（旧版只数总数，会漏过）

### 用例 7b：「前提假设」节内的硬约束不算泄漏
- 输入：`## 前提假设` 下写 `按键硬件固定在 PA5、对接上位机固定 115200 波特率`
- 期望：不报 `spec 里出现实现细节`，退出码 0

### 用例 7c：`<!-- impl-ok -->` 行内豁免
- 输入：需求节里一行以 `<!-- impl-ok -->` 结尾（含 `I2C1`），另一行写 `PA5` 无标记
- 期望：只报 `PA5` 一处警告，退出码 0

## check_intake.py

### 用例 8：受理单自洽
- 输入：落点 spec、验收场景「有变化 ｜ …」、重走范围含门 1 与门 2，五栏齐全
- 期望：输出 `受理单校验通过`，退出码 0

### 用例 9：门名不写空格
- 输入：重走范围写成 `门1 → plan → 门2 → …`
- 期望：退出码 0（比较前归一化空白）

### 用例 10：变更轮标题带轮次
- 输入：标题写成 `## r3 变更轮：…`，重走范围缺门 1
- 期望：能被识别并报 `重走范围却未包含 门 1`，退出码 1（旧版会静默跳过）

### 用例 11：落点与重走范围矛盾
- 输入：落点 spec，重走范围 `门 2 → tasks → implement`
- 期望：报未包含 门 1，退出码 1

### 用例 12：落点 plan 却含门 1
- 输入：落点 plan，重走范围含门 1
- 期望：报「重走范围不应包含 门 1」，退出码 1

### 用例 13：宪法落点
- 输入：落点 宪法、重走范围含门 1 与门 2、验收场景 有变化
- 期望：退出码 0

### 用例 14：缺栏
- 输入：缺「处置记录」（其余四栏齐全）
- 期望：报 `受理单缺少`，退出码 1

### 用例 15：验收场景与落点矛盾
- 输入：落点「仅实现」却写「有变化」
- 期望：报 `验收场景变了就是 spec 落点`，退出码 1

### 用例 16：验收场景取值非法
- 输入：验收场景栏写「待定」
- 期望：报「只能填「有变化」或「无变化」」，退出码 1

### 用例 17：旧写法拦截
- 输入：把「同时触及」单开一栏
- 期望：报 `「同时触及」应并入落点行`，退出码 1

### 用例 18：首轮建档
- 输入：没有变更轮段的 tasks.md
- 期望：只输出提示，退出码 0

### 用例 19：围栏内的示例不算数
- 输入：模板里的示例变更轮（在围栏内）
- 期望：退出码 0

### 用例 19a：澄清落点自洽
- 输入：落点 `澄清`、验收场景 `无变化`、重走范围 `门 1 → analyze`
- 期望：输出 `受理单校验通过`，退出码 0

### 用例 19b：澄清却写有变化
- 输入：落点 `澄清`、验收场景 `有变化`
- 期望：报 `澄清的定义就是验收场景不变`，退出码 1

### 用例 19c：澄清落点不得含门 2
- 输入：落点 `澄清`、重走范围 `门 1 → 门 2 → analyze`
- 期望：报 `重走范围不应包含 门 2`，退出码 1

## check_tasks.py

### 用例 20：作废任务格式正确
- 输入：`- [~] T026 ~~原描述~~ | FR-040/041` 且下一行是 `⤷ r2 作废：…`
- 期望：输出任务统计（已作废 1），退出码 0

### 用例 21：作废任务缺删除线
- 输入：`- [~] T099 某任务 | FR-001`，无删除线、无 ⤷ 行
- 期望：报两条错误（无删除线、缺 ⤷ 说明），退出码 1

### 用例 22：任务号被划进删除线
- 输入：`- [~] ~~T026 面板灯四态 | FR-040/041~~`
- 期望：报错并计入统计，退出码 1（旧版会既不报错也不计数）

### 用例 23：项目符号与缩进变体
- 输入：`- [ ]`、`* [ ]`、缩进的 `- [ ]` 三种写法
- 期望：统计到 3 条，退出码 0

### 用例 24：任务缺追溯
- 输入：任务既无 plan 落点也无 FR 编号
- 期望：报 `警告：… 没有 plan 落点或 FR 编号`，退出码 0

### 用例 25：围栏内的示例不算数
- 输入：Convergence 段的示例任务写在围栏内
- 期望：`未完成 0`，退出码 0

## check_landing.py（需要 git）

### 用例 26：真实改了验收场景却申报为下游
- 输入：相对基线改了某条验收场景，受理单落点「仅实现」、验收场景「无变化」
- 期望：报 `验收场景变了就是 spec 落点`，退出码 1

### 用例 27：声明与 diff 一致
- 输入：验收场景确有变化，受理单「有变化」且落点 spec
- 期望：输出「受理单声明一致」，退出码 0

### 用例 28：拿不到基线
- 输入：目标目录不是 git 仓库
- 期望：输出「无法与 git 对照」提示，退出码 0（不阻断，但要求人工确认）

### 用例 28a：基线是 HEAD 时给提交前提醒
- 输入：验收场景无变化、且 `--since` 用默认 HEAD
- 期望：提示用变更前的 ref 重跑（`--since <变更前的 commit/tag>`），退出码 0

## check_gate.py

### 用例 29：首轮门结论已批准
- 输入：`01-spec.md` 门 1 结论 = `approve ｜ 裁决人：张三 ｜ 日期：2026-10-09`
- 期望：输出 `门记录校验通过`，退出码 0

### 用例 30：首轮门结论还是待审
- 输入：模板初始状态 `**结论**：待审 ｜ 裁决人：<…> ｜ 日期：<…>`
- 期望：报 `仍是「待审」`，退出码 1（设计意图：没批就不许往下走）

### 用例 31：门结论缺裁决人 / 缺日期
- 输入：结论 = approve，但没有裁决人
- 期望：报 `缺「裁决人」`，退出码 1

### 用例 32：门结论为 reject
- 输入：结论 = reject
- 期望：报 `必须退回上游修`，退出码 1

### 用例 33：旧标题写法兼容
- 输入：小节标题写成 `## 评审门 1（review-spec）`
- 期望：退出码 0

### 用例 34：变更轮缺门的结论记录
- 输入：受理单重走范围含门 1 与门 2，却只写了门 1 的记录
- 期望：报 `却缺门 2 的结论记录`，退出码 1

### 用例 35：变更轮门记录齐全
- 输入：受理单重走范围含门 1，门 1 记录 = `approve ｜ 裁决人：张三 ｜ 日期：2026-10-09`
- 期望：退出码 0

### 用例 36：围栏内的示例门记录不算数
- 输入：示例门记录写在代码围栏内
- 期望：退出码 0

### 用例 37：结论里提到 reject 但首词是 approve
- 输入：结论 = `approve（上一轮 reject 已修复）｜ 裁决人：李工 ｜ 日期：2026-10-09`
- 期望：退出码 0（旧版按词表顺序先匹配 reject，会误判为驳回）

### 用例 38：脚本拦不住自批（预期行为，写进文档）
- 输入：结论 = `approve ｜ 裁决人：codex-agent ｜ 日期：2026-10-09`
- 期望：退出码 0——脚本只能拦占位符与待审，署名真实性靠人，故 SKILL.md 规定未获用户明确批准一律写 `待审`



### 用例 26：真实改了验收场景却申报为下游
- 输入：相对基线改了某条验收场景，受理单落点「仅实现」、验收场景「无变化」
- 期望：报 `验收场景变了就是 spec 落点`，退出码 1

### 用例 27：声明与 diff 一致
- 输入：验收场景确有变化，受理单「有变化」且落点 spec
- 期望：输出「受理单声明一致」，退出码 0

### 用例 28：拿不到基线
- 输入：目标目录不是 git 仓库
- 期望：输出「无法与 git 对照」提示，退出码 0（不阻断，但要求人工确认）

## 手工验证项

- [ ] 落点表、重走范围、状态机、写权限表**只在** `SKILL.md` 的「流程模型（唯一权威）」出现一次（全仓 grep 检查无第二份定义）
- [ ] `references/doc-set.md` 的「反向检验」是唯一出处，`references/drift.md` 只引用不复述
- [ ] `references/quality-mechanisms.md` 不再出现 `requirements-quality.md`（孤儿引用已删）
- [ ] 每个模板都能通过对应校验器（`01-spec.md` → check_spec；`03-tasks.md` → check_intake / check_tasks）
- [ ] `README.md` 不含落点表的第二份拷贝
- [ ] 模板在**未批准前**跑 `check_gate.py` 必然报「待审」或「缺裁决人」——这是设计意图，不是缺陷（批准后把结论改成 `approve` 并填裁决人、日期）
- [ ] 分工检查：`SKILL.md` 里没有设计论证长段；真实事故叙事只出现在 `references/rationale.md`
- [ ] `quality-mechanisms.md` 不再复述 `SKILL.md` 的「两类关卡」表（2.2.0 改为指向）
- [ ] 模板里的受理单示例与 `SKILL.md` 的落点取值一致（含 `澄清`）
- [ ] 落点 `澄清` 在 `SKILL.md` 落点表、`check_intake.py`、`landing.md`、`03-tasks.md` 模板四处一致
