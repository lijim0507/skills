# 规范驱动开发（SDD）

## 四条内核

1. **先文档后代码**——任何要改代码的事，先改文档，再动代码。
2. **三顶帽子**——01 产品经理、02 技术总监、03 任务负责人，一次只戴一顶。
3. **角色各有决定权**——01 决定产品做什么，02 决定用什么方式实现，03 决定按什么顺序、由谁、做到什么程度。文档只记录本角色的决定。
4. **人保留否决权**——门 1、门 2、验收由人裁决，agent 不代签。

## 角色与读取范围

派活只给对应角色页和模板，不要给整份技能。

| 阶段 | 角色 | 只读 | 产出 |
| --- | --- | --- | --- |
| 01 | 产品经理 | 需求 + `roles/01-pm.md` + `templates/01-spec.md` | `01-spec.md` |
| 02 | 技术总监 | 01 + 代码事实 + `roles/02-architect.md` + `templates/02-*.md` | `02-plan*.md` |
| 03 | 任务负责人 | 01 + 02 + `roles/03-owner.md` + `templates/03-tasks.md` | `03-tasks.md` |
| 实现 | 执行者 | 03 的任务卡 + 代码 | 代码与证据 |
| 评审 | 挑刺者 | 产物 + 检查清单 | 审查意见 |

角色不是文档填写员。动笔前先问：这个决定该由谁做？对外承诺归 01，实现方式归 02，怎么拆、谁做、按什么顺序归 03。

## 主流程

| 步骤 | 做什么 | 完成标志 |
| --- | --- | --- |
| S0 | 没有 `SDD/` 就按模板铺 00~04 | 五份骨架就位 |
| S1 | 写 01 | 结构完整，可交门 1 |
| S2 | 门 1（停） | 人写 approve |
| S3 | 写 02 与子件 | 结构完整，可交门 2 |
| S4 | 门 2（停） | 人写 approve |
| S5 | 写 03 | 结构完整，可交开工检查 |
| S6 | analyze + 开工前检查 | 未闭合项为 0 |
| S7 | 实现 | 任务卡逐条 `[x]`，留证据 |
| S8 | converge | 无缺口或追加任务 |
| S9 | 验收（停） | 真机跑过，人签字 |

## 落点表

| 动了什么 | 从哪重走 |
| --- | --- |
| 00 宪法 | 门 1 → 门 2 → 03 → analyze → 实现 → 验收 |
| 01 规格 | 门 1 → 门 2 → 03 → analyze → 实现 → 验收 |
| 02 方案 | 门 2 → 03 → analyze → 实现 → 验收 |
| 03 任务 | 开工检查 → 实现 → 验收 |
| 只动代码 | converge → 验收 |

## 阶段收尾顺序

写文档 → 跑 lint → 独立评审 → 人签字。

- lint 只证明结构完整，不证明内容合格；脚本输出是「结构检查通过 · 语义未验证」。
- 门 1 / 门 2 的结论只由人写；汇报时不说「检查通过」。
- 新输入先判归属：外部承诺进 01，实现与系统集成进 02，可分配工作进 03。

## 四个交接动作

- **接手先复述**：02 / 03 动笔前，先写三句话——我拿到了什么、据此要做什么、还缺什么。写不出来就是上游不自足，退回，不靠猜补。
- **退回就改上游**：不可行、方案缺口、需求矛盾，回上游改正文，不在下游降级；改了什么由修订记录承接，不确定的留在未决项。
- **评审要隔离**：评审者只拿产物和清单，不参加写作过程；产出「查了哪些项、发现几条、每条在哪」。「未发现问题」不算结论。
- **改动即作废**：门签字带正文版本；正文一改，结论回到「待审」，由人重新签字。

## 文档集

```text
SDD/
├── 00-constitution.md       可判定原则
├── 01-spec.md               定位 / 故事 / FR / 外部契约 / 门 1 / 交接
├── 02-plan.md               可行性 / 模块 / 决策 / 风险 / 验证 / 门 2
├── 02-plan-research.md      决策与备选
├── 02-plan-data-model.md    实体 / 状态 / 写权限
├── 02-plan-contracts.md     模块清单 / 依赖 / 契约
├── 03-tasks.md              批次 / 任务卡 / 映射 / 检查
└── 04-converge.md           收敛结论与验收记录
```

## 轻量使用

小项目可只保留 01 / 02 / 03；00 并入 README；04 只写验收记录。轻量的是文档量，不是判断量，门不能省。

## 不确定就标

需求不确定标 `[NEEDS CLARIFICATION]`，不猜着写；执行不确定标 `blocked`，写明卡在哪、等谁。没定的不进正文，定了再改，改了就重签。

## 完成判据

03 无 `[ ]` 残留；验收按 01 的场景在真实环境跑过并由人签字。
