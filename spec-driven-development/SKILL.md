# 规范驱动开发（SDD）

## 三条内核

其余规则都是它们的推论。看到一条规则时，先问它从哪条内核推出来；推不出来的，多半是不该有的补丁。

1. **先文档后代码**——任何要改代码的事，先把文档改掉，再动代码。这是整套机制的支点：没有文档 diff，落点就推不出来。
2. **文档各有边界**——`01-spec.md` 只写 what/why（零技术），`02-plan.md` 只写 how，`03-tasks.md` 只写任务。边界守住了，「落点」才是事实而不是判断。
3. **人保留否决权**——门 1、门 2、验收由人裁决；agent 负责发现，人负责裁决。

## 文档集

```text
SDD/
├── 00-constitution.md      项目原则：编号 · 可判定 · 注明出处
├── 01-spec.md              what/why + 门1清单与结论 + 修订记录
├── 02-plan.md              how + 门2清单与结论 + 修订记录
│   ├── 02-plan-research.md     Phase 0：每个决策 + 被否决的方案
│   ├── 02-plan-data-model.md   Phase 1：实体、状态迁移
│   └── 02-plan-contracts.md    Phase 1：接口契约
├── 03-tasks.md             任务 · 覆盖映射 · analyze 交叉检查 · 开工前检查 · 收敛追加段 · 修订记录
└── 04-converge.md          本轮收敛结论
```

每份文档写什么、谁写、谁消费 → `references/doc-set.md`

## 落点：位置定重走，语义定实质

改了哪份文档，就从对应的门开始往下走：

| 动了什么               | 从哪重走                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `00-constitution.md` | 宪法修订 → 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收 |
| `01-spec.md`         | 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收             |
| `02-plan*.md`        | 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收                    |
| `03-tasks.md`        | 开工前检查 → implement → converge → 验收                                               |
| 只动代码               | converge → 验收                                                                          |
| 同时动多份             | 取最上游那一处                                                                            |

**语义定实质**：改的是 `01-spec.md` 的措辞、功能全量等价（术语统一、错别字、把含糊句写清楚），不算需求修订——不走门 1，只在修订记录留一句「语义未变」。

## 三道关卡

|        | 门 1                                  | 门 2                 | 验收                     |
| ------ | ------------------------------------- | -------------------- | ------------------------ |
| 谁判   | 人（产品视角）                        | 人（技术视角）       | 人                       |
| 审什么 | 每条需求能不能判做没做到              | 可行吗、逐条对答宪法 | 按 01 的验收场景实测     |
| 通过   | `approve ｜ 裁决人：… ｜ 日期：…` | 同左                 | 结论落`04-converge.md` |

**门是阻塞点**：写完就停下等明确批准，**不得自行填写 approve**，未获批不得进入下一步。`reject` → 退回该门上游修 → 修完重跑该门。

写权限——**都不允许「就地改到通过」**：

| 环节         | 谁     | 写权限                                                         |
| ------------ | ------ | -------------------------------------------------------------- |
| 门1 / 门2    | 人     | 清单勾选与结论行**只由裁决人写**                         |
| `analyze`  | agent  | 只写`03-tasks.md` 的「analyze 交叉检查」节，不改被检查内容   |
| 开工前检查   | 评审者 | 只统计已勾 / 未勾；有未勾就**停下问**，不得自己打勾      |
| `converge` | agent  | **只追加**任务到 `03-tasks.md`；不改代码、不改文档正文 |

## 状态机

```text
S0 没有 SDD/ → 用 templates/ 落骨架，立即进流程
  ↓
S1 01-spec ──🚦门1── approve → S2 ／ reject → 回 S1
  ↓
S2 02-plan（含 Phase 0/1 子件、宪法逐条对答）──🚦门2── approve → S3 ／ reject → 回 S2
  ↓
S3 03-tasks（每条任务挂 FR）
  ↓
S4 ⚙️ analyze ── 未闭合项必须严格递减到 0；发现问题 → 回上游修
  ↓
S5 ⚙️ 开工前检查 ── 全勾 → S6 ／ 有未勾 → 停下问
  ↓
S6 implement ── 任务 [ ] → [x]
  ↓
S7 ⚙️ converge ── 有缺口 → 追加任务 → 回 S6 ／ 无缺口 → S8
  ↓
S8 🚦 验收 ── 按 01 的验收场景在真实设备上跑一遍，人签字
  ↓
完成
```

## 执行规则

1. **先判落点**——这次改动动了哪份文档？同时触及多份取最上游。判不准按上游：代价不对称——需求变更溜过去是失控，多走一遍只是浪费。
2. **先铺纸**——没有 `SDD/` 就用 `templates/` 落骨架：把 `00` ~ `04` 写进项目的 `SDD/`，**删掉模板里的示例段**，然后从 S1 开始。
3. **门要停**——四步做完，不要只说一句「请批准」就自己往下走：
   - **停**：写完 `01-spec`（或 `02-plan`）后，不在同一步里继续改下游文档或代码
   - **请**：明确说出「请审批门 N：approve / reject」，然后**结束本轮**等回话
   - **记**：只有回话里出现明确批准时才写 `approve ｜ 裁决人：<用户> ｜ 日期：<当天>`；**裁决人写用户，不写你自己**。没表态或「你看着办」→ 保持 `待审`
   - **驳**：reject 或提出修改 → 退回该门上游修，修完重跑该门，不得带病继续
4. **记账只记 diff 看不到的**——改了什么 diff 里有；修订记录写**为什么、依据什么、谁批的**。一次改动跨多份文档时，用同一个轮次号（`r2`）串起来。
5. **不许静默猜测**——需求不确定标 `[NEEDS CLARIFICATION]`，执行不确定标 `blocked`，写明卡在哪、等谁。
6. **守住写权限**——见上表。`implement` 对开工前检查清单只读；`converge` 只追加。

## When to use

- 会改动代码、且值得留下规格痕迹的变更：新增功能、修改行为、修缺陷、重构
- 需求变更、方案变更、范围裁剪
- 项目第一次用：还没有 `SDD/` 目录，需要铺纸
- 用户提到「按 SDD」「规范驱动」「先写规格」

## When NOT to use

- 纯问答、代码解释、只读操作（看日志、搜代码、读文件）
- 与代码变更无关的文档整理与格式调整
- **规模下限**：单文件、不改变任何外部可观察行为的小改（错别字、注释、日志文案、格式化），且用户没有点名要走 SDD——直接改
- 用户明确表示这个项目不建文档集

## Output

- 更新后的文档集 `SDD/`：按落点重走后的 `01-spec.md` / `02-plan*.md` / `03-tasks.md` / `04-converge.md`，以及各文档的修订记录
- 按任务清单完成的代码变更：任务逐条勾选 `[x]`
- `04-converge.md`：本轮收敛结论（发现了什么、怎么处置、结论是 `Converged` 还是 `Tasks appended`）
- **Done When**：`03-tasks.md` 无 `[ ]` 残留，且验收已按 `01-spec.md` 的验收场景在真实设备上跑过、由人签字
