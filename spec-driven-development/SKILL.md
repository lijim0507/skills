# 规范驱动开发（SDD）

## Description

用「先文档后代码」约束一切会改动代码的工作。四条内核，其余规则都是它们的推论；看到一条规则时，先问它从哪条内核推出来，推不出来的多半是不该有的补丁。

1. **先文档后代码**——任何要改代码的事，先把文档改掉，再动代码。这是整套机制的支点：没有文档 diff，落点就推不出来。
2. **三顶帽子，三段交接**——`01-spec.md` 是产品经理的产物，`02-plan.md` 是技术总监的产物，`03-tasks.md` 是任务负责人交给执行者的工单。每顶帽子只回答一个问题，不替下一顶帽子做决定。
3. **文档各有边界**——`01-spec.md` 只写外部承诺（what/why + 外部契约，零内部实现），`02-plan.md` 只写 how，`03-tasks.md` 只写可分配的任务。边界守住了，「落点」才是事实而不是判断。
4. **人保留否决权**——门 1、门 2、验收由人裁决；agent 负责发现，人负责裁决。

## 三种帽子，三段交接

| 阶段 | 帽子 | 只回答 | 产物 | 交给谁 |
| --- | --- | --- | --- | --- |
| spec | 产品经理 | 谁在什么场景下遇到什么问题，什么算做对了？ | `01-spec.md` | 技术总监 |
| plan | 技术总监 | 在现有约束下怎么做，为什么这样最合适？ | `02-plan*.md` | 任务负责人 |
| tasks | 任务负责人 | 谁在什么边界内做什么，怎么算完成？ | `03-tasks.md` | 实现者 |
| implement | 实现者 | 按工单交付可验证的结果 | 代码 + 证据 | 验收人 |

一个人可以戴多顶帽子，但**一次只戴一顶**。写 spec 时假装不懂技术；写 plan 时才允许谈内部实现；拆任务时不要重新论证架构。每段末尾写交接摘要，只写下一顶帽子必须知道、但 diff 里看不出来的判断。细则见 `references/roles.md` 和 `references/handoffs.md`。

## When to use

适用于：

- 会改动代码、且值得留下规格痕迹的变更：新增功能、修改行为、修缺陷、重构
- 涉及外部消费者契约的 API / CLI / SDK / 协议 / 数据 schema / SLO 变更
- 需求变更、方案变更、范围裁剪
- 项目第一次用：还没有 `SDD/` 目录，需要铺纸
- 用户提到「按 SDD」「规范驱动」「先写规格」

## When NOT to use

不适用于：

- 纯问答、代码解释、只读操作（看日志、搜代码、读文件）
- 与代码变更无关的文档整理与格式调整
- **规模下限**：单文件、不改变任何外部可观察行为的小改（错别字、注释、日志文案、格式化），且用户没有点名要走 SDD——直接改
- 用户明确表示这个项目不建文档集

## 轻量使用

小项目、单人项目或一次性改动不必把五个文件都写满：

- 至少保留 `01-spec.md` / `02-plan.md` / `03-tasks.md`；涉及模块间契约时再加 `02-plan-contracts.md`，没有就写明「无内部契约」
- `00-constitution.md` 可以并入项目 README 的「项目原则」节
- `04-converge.md` 可以只写验收记录
- Phase 0 / Phase 1 子件、非功能属性、宪法检查等字段，与本次改动无关就删掉

**门 1、门 2、验收不能省**；轻量的是文档量，不是判断量。

## 软件普适性

核心规则与行业无关。选模板时不要按「公司属于哪个行业」选，而按**这次变更的外部可观察面**选：

- 面向终端用户的产品：用户看到的行为、交互、兼容性、可访问性
- 平台 / 内部服务：下游团队或系统依赖的 API、状态码、SLO、数据一致性
- 库 / CLI / SDK：开发者依赖的命令、参数、退出码、公开 API、版本兼容
- 内部工具 / 自动化：操作者和维护者依赖的输入输出、幂等、失败恢复
- 原型 / 实验：要回答的产品问题是否被回答，而不是生产级 SLO
- 嵌入式 / 设备：现场环境中的行为、时序、功耗、升级与回滚
- 数据 / ML：数据口径、模型指标、延迟、漂移、可解释性

一个项目涉及多个领域时，以**这次变更的主要外部契约**为准；跨端变更分别写清各端的验证环境。详细对照见 `references/domains.md`。模板里的字段只是提示，与领域无关的字段留空或删掉，不要硬填。

## Input

- **变更请求**（必填）：要改什么、为什么改。含糊时标 `[NEEDS CLARIFICATION]`，不要猜
- **目标项目**（可选）：默认当前工作目录。文档集是项目根下的 `SDD/`；已存在就先读它，不重建
- **约束**（可选）：期限、兼容性、运行环境与资源限制
- **既有文档集**（可选）：有就沿用，**不新开一套**

## Instructions

文档集（项目根下的 `SDD/`，建项时落一套，之后所有改动都在同一套上改）：

```text
SDD/
├── 00-constitution.md      项目原则：编号 · 可判定 · 注明出处
├── 01-spec.md              what/why + 外部契约 + 门1清单与结论 + 交接给技术总监 + 修订记录
├── 02-plan.md              how（含模块划分）+ 门2清单与结论 + 交接给任务拆解 + 修订记录
│   ├── 02-plan-research.md     Phase 0：每个决策 + 被否决的方案
│   ├── 02-plan-data-model.md   Phase 1：实体、状态迁移、归属与写权限
│   └── 02-plan-contracts.md    Phase 1：模块清单 · 依赖方向 · 模块间契约
├── 03-tasks.md             任务分配说明 · 执行批次 · 任务 · 任务卡 · 覆盖映射 · analyze 交叉检查 · 开工前检查 · 收敛追加段 · 修订记录
└── 04-converge.md          本轮收敛结论
```

落点表——改了哪份文档，就从对应的门开始往下走：

| 动了什么               | 从哪重走                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `00-constitution.md` | 宪法修订 → 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收 |
| `01-spec.md`         | 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收             |
| `02-plan*.md`        | 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收                    |
| `03-tasks.md`        | 任务交接检查（开工前检查）→ implement → converge → 验收                                 |
| 只动代码               | converge → 验收                                                                          |
| 同时动多份             | 取最上游那一处                                                                            |

按这个顺序执行：

1. **先铺纸**——没有 `SDD/` 就用 `templates/` 落骨架：把 `00` ~ `04` 写进项目的 `SDD/`，**删掉模板里的示例段**，然后继续第 2 步。
2. **判落点**——这次改动动了哪份文档？同时触及多份取最上游。判不准按上游：代价不对称——需求变更溜过去是失控，多走一遍只是浪费。
3. **产品经理写 `01-spec.md`**——结构和写法以 `examples/todo-cli/SDD/01-spec.md` 为范本：产品根（消费者 + 问题 + 使用价值 + 场景 + 现有替代 + 成功信号）→ 用户故事（场景与结果 + 解决方向）→ FR → 验收场景 → 成功标准。先填产品根，再写故事（每条引用一个 R），再写 FR、验收场景、成功标准和外部契约。**不写框架、模块划分、内部标识、私有参数、表结构**——这些是技术总监的判断。
4. **停门 1**——审的是「spec 是否可验收」：每条需求能否判定、消费者/场景/非目标是否清楚、外部契约能否验证。四步做完，别只说一句「请批准」就往下走：
   - **停**：不在同一步里继续改下游文档或代码
   - **请**：说出「请审批门 1：approve / reject」，然后**结束本轮**等回话
   - **记**：只有回话里出现明确批准时才写 `approve ｜ 裁决人：<用户> ｜ 日期：<当天>`；**裁决人写用户，不写你自己**。没表态或「你看着办」→ 保持 `待审`
   - **驳**：reject → 退回 `01-spec.md` 修，修完重跑门 1，不得带病继续
5. **技术总监写 `02-plan.md`**——方案总览 → **需求可行性核对（逐条 FR / 外部契约：可行 / 有条件 / 不可行；不可行回 `01` 改，不在 plan 里私自降级）** → 技术上下文 → 模块划分（必填） → 数据模型与内部契约（Phase 1 子件） → 质量属性与约束 → 关键决策与备选 → 风险与应对 → 交付 / 迁移 / 回滚 → 验证手段 → 宪法检查（逐条对答 `00-constitution.md`）→ 复杂度跟踪 → 待办与偏差登记 → 门 2 清单与结论 → **交接给任务拆解** → 修订记录。**不重复 `01` 的需求与外部契约**；内部契约见 `02-plan-contracts.md`（模块清单 · 依赖方向 · 模块间契约）。需求有变化回 `01` 改，不在这里私了。
6. **停门 2**——同第 4 步的四步；审的是「需求可行性逐条回应了吗、模块边界清楚吗、方案可行吗、内部契约自洽吗、风险与回滚想清楚了吗、逐条对答过宪法吗」。reject → 退回 `02-plan*.md` 修。
7. **任务负责人拆 `03-tasks.md`**——先写任务分配说明（执行者先读什么、代码范围、通用 DoD、验证命令、阻塞找谁），再排执行批次，再拆任务。每条任务挂 `FR-0xx`、外部契约项、风险项，或显式标 `| 流程`（建档、清理等非需求任务）。**非平凡任务必须有任务卡**：执行者 / 目标 / 范围 / 输入 / 产出 / 完成判据（DoD）/ 验证 / 依赖 / 可并行 / 风险回滚。粒度判据：**一个不知道来龙去脉的执行者，只看这一条任务卡，能做完并自己判定做完没做完。**
8. **跑 `analyze`**——跨产物互查。**只写「analyze 交叉检查」节**，不改被检查内容；发现问题回上游修（需求回 `01`、设计回 `02`、任务回 `03`），**未闭合项必须严格递减到 0**。某轮不降反增 → 立即停下回上游，说明在打转。
9. **过任务交接检查（开工前检查）**——评审者勾：每条 FR 有任务覆盖、依赖无环、每条外部契约有验证手段、验收手段可执行、每条任务有任务卡和 DoD、任务范围不重叠、执行环境就绪。`implement` 对它**只读**：发现有未勾就**停下询问**，不得自己打勾。
10. **`implement`**——按任务卡写代码，逐条把 `[ ]` 改成 `[x]`，并留下验证证据。
11. **跑 `converge`**——**只追加**：有缺口就往 `03-tasks.md` 的「收敛追加」段追加任务，然后回第 10 步；无缺口 → `Converged`（判据：除本次追加外 `03-tasks.md` 逐字节不变）。结论写进 `04-converge.md`。
12. **停验收**——`converge` 只证「代码没背叛文档」，证不了「在目标环境里真的做到了」。由人按 `01-spec.md` 的验收场景和外部契约在**真实运行环境**（如浏览器/设备矩阵、生产等价服务环境、目标 OS、评测集）中跑一遍并签字，结论落 `04-converge.md`。**这一步没有替代品。**
13. **守住写权限**——**都不允许「就地改到通过」**：门结论只由裁决人写；`analyze` 只写自己那一节；`converge` 只追加任务、不改代码与文档正文。
14. **记账只记 diff 看不到的**——改了什么 diff 里有；修订记录写**为什么、依据什么、谁批的、这一轮到哪为止**。一次改动跨多份文档时，用同一个轮次号（`r2`）串起来。
15. **措辞订正免门 1**——改的是 `01-spec.md` 的措辞、功能全量等价（术语统一、错别字、把含糊句写清楚）→ 不算需求修订，只在修订记录留一句「语义未变」。这条豁免靠「验收场景段落逐字节未变」兜底，拦不住换了说法的语义漂移。
16. **不确定就显式标**——需求不确定标 `[NEEDS CLARIFICATION]`，执行不确定标 `blocked`，写明卡在哪、等谁，不许静默猜测。

状态图（第 1 ~ 12 步的压缩）：

```text
S0 没有 SDD/ → 用 templates/ 落骨架，立即进流程
  ↓
S1 01-spec（产品经理）──🚦门1── approve → S2 ／ reject → 回 S1
  ↓
S2 02-plan（技术总监：可行性、模块、风险、回滚）──🚦门2── approve → S3 ／ reject → 回 S2
  ↓
S3 03-tasks（任务负责人：批次 + 任务卡）
  ↓
S4 ⚙️ analyze ── 未闭合项必须严格递减到 0；发现问题 → 回上游修
  ↓
S5 ⚙️ 任务交接检查 ── 全勾 → S6 ／ 有未勾 → 停下问
  ↓
S6 implement ── 按任务卡交付，任务 [ ] → [x]
  ↓
S7 ⚙️ converge ── 有缺口 → 追加任务 → 回 S6 ／ 无缺口 → S8
  ↓
S8 🚦 验收 ── 按 01 的验收场景和外部契约在真实运行环境里跑一遍，人签字
  ↓
完成
```

结构范本：`examples/todo-cli/SDD/`（可跑通的完整样例，四道检查全过；写 spec 时直接看它）。细则：`references/roles.md`（三顶帽子与质量判据）｜`references/handoffs.md`（四段交接与任务卡模板）｜`references/doc-set.md`（文档职责与内容归属）｜`references/landing.md`（落点与记账）｜`references/gates.md`（关卡规则、写权限、停机动作）｜`references/checks.md`（机器检查与脚本用法）｜`references/domains.md`（软件形态适配与示例）。

脚本在**技能目录**里，不在目标项目里。运行：`python <技能目录>/scripts/check_spec.py <项目>/SDD/01-spec.md`（规格结构）｜`check_tasks.py`（任务、任务卡与开工前检查）｜`check_chain.py`（故事 → FR → 任务不断链）｜`check_plan.py`（模块划分、契约引用、依赖环）。

## 维护这套技能

- 改模板或脚本后，先跑 `examples/todo-cli/SDD` 的四道检查；样例全绿再算改完
- 新增领域或软件形态，先补 `references/domains.md` 的对照行，不要改核心规则
- 新增规则必须能追溯到四条内核之一；追溯不到就删掉，别把补丁堆成流程
- 发现某条规则在真实项目里反复造成摩擦，先改规则，再改模板和脚本

## Output

- 更新后的文档集 `SDD/`：按落点重走后的 `01-spec.md` / `02-plan*.md` / `03-tasks.md` / `04-converge.md`，以及各文档的修订记录
- `01-spec.md` 按范本补齐的产品根、用户故事（场景与结果 + 解决方向）、FR、验收、成功标准和外部契约（如有），以及「交接给技术总监」摘要
- `02-plan.md` 的「需求可行性核对」「交接给任务拆解」摘要
- `03-tasks.md` 的任务分配说明、执行批次、任务卡
- 按任务清单完成的代码变更：任务逐条勾选 `[x]`，并保留验证证据
- `04-converge.md`：本轮收敛结论（发现了什么、怎么处置、结论是 `Converged` 还是 `Tasks appended`）
- **Done When**：`03-tasks.md` 无 `[ ]` 残留，且验收已按 `01-spec.md` 的验收场景和外部契约（如有）在真实运行环境中跑过、由人签字
