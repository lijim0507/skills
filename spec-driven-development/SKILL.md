# 规范驱动开发（SDD）

## Description

以「先定规格、再动代码」的流程约束软件变更：每一步都落在文档上，每一次改动都要过关卡，保证变更可追溯、可验收、可收敛。

三条内核，其余规则都是它们的推论（由来与理由见 `references/rationale.md`）：

- **一个判据**：改它，验收场景变没变？
- **一条链**：`spec → plan → tasks → 实现`，位置决定成本。
- **一份证据**：每一种「已完成 / 已通过」的声明都要挂可核对的证据，谁写什么由写权限划定。

项目建项时确定一套文档集，之后所有变更都在**同一套**上改和记录，不新开文档集：

```text
SDD/
├── 00-constitution.md      项目原则：可判定、编号、注明出处
├── 01-spec.md              只写 what / why（含门 1 清单与结论）
├── 02-plan.md              技术方案（how，含门 2 清单与结论）
│   ├── 02-plan-research.md     Phase 0：消化所有 [NEEDS CLARIFICATION]
│   ├── 02-plan-data-model.md   Phase 1：实体、状态迁移
│   └── 02-plan-contracts.md    Phase 1：接口契约
├── 03-tasks.md             任务 + analyze 交叉检查 + 变更轮段 + Convergence 段
└── 04-converge.md          收敛报告 + 变更轮处置记录
```

各文档职责与内容归属判据见 `references/doc-set.md`。

## 流程模型（唯一权威）

> **本节是唯一权威来源。** `references/*` 与 `README.md` 只解释、不复述这些表；发现不一致时以本节为准。

### 判据：改它，验收场景变没变？

锚点是 `01-spec.md` 用户故事里的 **验收场景**（格式固定、可观察、可 diff）。同一条判据用在四个地方：

| 调用点   | 时机                   | 问法                                                                                          |
| -------- | ---------------------- | --------------------------------------------------------------------------------------------- |
| 落点判定 | 改动之前               | 这次改动会不会改到某条验收场景？                                                              |
| 漂移分类 | 发现文档与实现不一致时 | 是验收场景变了（改 spec），还是实现没做到（改实现），还是它本来就不该写在 spec（搬去 plan）？ |
| 范围裁剪 | 需求退场时             | 需求消失 → 验收场景消失 → spec 落点                                                         |
| 内容归属 | 写文档时               | 删除这段，验收还做得成吗？做得成 → 属于 plan                                                 |

### 一条链与落点表

文档集是一串上下游依赖：改动落在哪一环，决定下游有多少东西可能失效——所以也决定从哪重走（**位置决定成本**）。

| 依次问                                                     | 落点             | 重走范围                                                                                          |
| ---------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| 项目原则 / 纪律会不会变？（宪法）                          | **宪法**   | Governance 修订 → 门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge |
| 验收场景会不会变？                                         | **spec**   | 门 1 → plan → 门 2 → tasks → analyze → checklist → implement → converge                    |
| 只是把 spec 写清楚、验收场景不变？（澄清）                 | **澄清**   | 门 1 → analyze                                                                                   |
| 方案会不会变？（引脚 / 外设 / 接口 / 数据模型 / 资源分配） | **plan**   | 门 2 → tasks → analyze → checklist → implement → converge                                    |
| 只是既有任务的增删改？                                     | **tasks**  | checklist → implement → converge                                                                |
| 都不涉及，只是实现修正？                                   | **仅实现** | converge                                                                                          |

**澄清**只用于「改的是 `01-spec.md` 的措辞，验收场景一个字不变」——没有这一档，文字订正会被判成「仅实现」，塞进 converge。

两条补充：**判不准按上游**（当作 spec）；**跨多层取最高**（宪法 > spec > 澄清 > plan > tasks > 仅实现，重走范围必须覆盖最上游那处）。

### 重走顺序

```text
S0 建项 →（提取宪法 + 用户 ratify）→ S1 spec →门 1→ S2 plan →门 2→ S3 tasks →analyze→ S4 待实现 →checklist→ S5 实现 →全部 [x]/[~]→ S6 收敛 →converge→ S7 完成
```

门 1 / 门 2 是**阻塞点**：`approve → 下一步`；`reject → 回上游修`。`analyze` 未闭合项为 0 才进 S4；`converge` 有缺口则追加任务回 S5。

**变更轮**：改动落在链的哪一环，就从对应状态重走；**没动过的部分沿用上次结论，不重审**——门只有一道，变的是审查范围随 diff 收缩。完整状态图见 `references/quality-mechanisms.md`。

### 两类关卡

|        | 人审门（门 1 / 门 2）                                                                                | 机器守卫（analyze / converge + 脚本）          |
| ------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 谁来判 | **人**：approve / reject                                                                       | agent / 脚本，按确定的检查项                   |
| 阻塞性 | **是阻塞点**：写完必须停下等明确 approve，未获批不得进入下一步，**不得自行填写 approve** | 不阻塞人，但发现问题必须回上游修，重跑直到干净 |
| 失败时 | reject → 退回该门上游修 → 修完重跑该门                                                             | 见下表写权限                                   |

**共同点：都不允许「就地改到通过」**——问题必须回到拥有它的地方解决。

### 写权限与证据

| 环节          | 谁     | 写权限                                                                                | 退出证据                                            |
| ------------- | ------ | ------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 门 1          | 人     | `01-spec.md` 的「门 1」清单勾选与结论行，只由评审者写（变更轮写在受理单的门 1 行）  | 结论 =`approve` + 裁决人 + 日期，且清单全勾       |
| 门 2          | 人     | `02-plan.md` 的「门 2」清单勾选与结论行（变更轮写在受理单的门 2 行）                | 结论 =`approve` + 裁决人 + 日期                   |
| `analyze`   | agent  | **只写 `03-tasks.md` 的「analyze 交叉检查」一节**；不改需求 / 方案 / 任务内容 | 该节未闭合项 = 0                                    |
| `checklist` | 评审者 | 清单在`01-spec.md` 门 1 内，勾选权归评审者；`implement` 对它**只读**        | 清单 Checked = Total                                |
| `converge`  | agent  | **只追加**：唯一写入是往 `03-tasks.md` 追任务；不改代码、不改文档正文         | `04-converge.md` 结论行；除追加外任务行逐字节不变 |

## When to use

适用于：

- 项目建项：绿地新项目，或为已有代码的项目补建文档集
- 会改动代码、且值得留下规格痕迹的变更请求：新增功能、修改现有行为、修复缺陷、重构
- 需求变更、方案变更、范围裁剪
- 用户明确要求走 SDD 流程，或提到「规范驱动」「先写规格」

## When NOT to use

不适用于：

- 纯问答、代码解释、阅读理解等不产生变更的任务
- 只读操作（查看日志、搜索代码、读取文件）
- 与代码变更无关的文档整理与格式调整
- **规模过小的改动**：单个文件、不改变任何外部可观察行为（错别字、注释、日志文案、格式化），且用户没有点名要走 SDD——直接改，不要触发建项
- **用户不想为该项目建文档集**：按第 1 步问过之后用户表示不需要，就退出本流程，本次改动按普通方式处理

## Input

从对话上下文中获取以下信息：

- **变更请求**（必填）：要改什么、为什么改
- **目标项目或模块**（可选）：默认当前工作目录
- **既有文档集**（可选）：默认项目根下的 `SDD/`；已存在就先读它，不重建
- **约束条件**（可选）：期限、兼容性、硬件资源等

变更请求含糊时，用 `[NEEDS CLARIFICATION]` 或 `blocked` 显式标记并向用户确认，**不要猜**。项目还没有文档集时，先按第 1 步问用户「要不要为这个项目建 SDD 文档集」，**用户同意才建**；用户不需要就退出本流程。

## Instructions

1. **起步（仅建项时）**——绿地新项目：提取宪法 → 用户 ratify → spec → 门 1 → plan → 门 2 → tasks。棕地或回溯：以实现为事实源反推宪法与 spec，偏差进「待办与偏差登记」→ **逐条确认偏差判定**（只确认偏差，不确认正常内容）→ 走门 1 / 门 2。用模板生成文档后，先删掉模板里的示例段（`03-tasks.md` 的示例变更轮与示例受理单），再跑脚本自检。详见 `references/bootstrap.md`。

   还没有文档集时**不要直接建**：先问用户是否要为这个项目建立 SDD 文档集，说清代价（宪法 + spec + 两道门 + plan + tasks，一次完整周期）与收益（变更可追溯、可验收）。用户不需要就退出本流程。
2. **判落点**——用上面的判据与落点表，依次问，第一处「会变」的就是落点。判不准按上游；跨多层取最高。怎么判、为什么这么判见 `references/landing.md`。
3. **写受理单**——写进 `03-tasks.md` 新增变更轮段的开头：**五栏齐全**（落点 / 验收场景 / 重走范围 / 判定依据 / 处置记录），再加**本轮经过的每一道门的结论行**（经过哪道写哪道，格式 `approve ｜ 裁决人：… ｜ 日期：…`，未批就写 `待审`）。**完整示例见 `references/landing.md`**；写完用 `check_intake.py` 与 `check_gate.py` 自检。

   「验收场景」栏只能填 **有变化** 或 **无变化**；落点是 plan / tasks / 仅实现却填「有变化」、或落点是 澄清 却填「有变化」→ 受理单自相矛盾，`check_intake.py` 直接报错。

   有 git 时用 `check_landing.py` 把这一栏与真实 diff 对照：**在提交前跑，并用变更前的 ref 作基线**（`--since <变更前的 commit>`）。默认的 `HEAD` 在改动已提交后只会看到空 diff，脚本会退化成一句提示，安全网失效。

   门结论的落点只有两处：**首轮**写在被审文档的门小节里（门 1 在 `01-spec.md`、门 2 在 `02-plan.md`）；**变更轮**写在受理单里。受理单**不要放进代码围栏**——校验器忽略围栏内的内容。
4. **随重走路径走**——从落点对应的第一道门开始。**门是阻塞点**，按下面四步做，不要只说一句「请批准」就自己往下走：

   - **停**：写完 spec（或 plan）后，不在同一步里继续改 plan / tasks / 代码；把受理单与被审文档的 diff 一并呈现
   - **请**：明确说出「请审批门 N：approve / reject」，然后**结束本轮**等用户回话
   - **记**：只有用户回话里出现明确批准（「批准」「approve」「可以」等）时，才把结论行写成 `approve ｜ 裁决人：<用户名> ｜ 日期：<当天>`；**裁决人写用户，不写你自己**。用户没表态或只说「你看着办」→ 保持 `待审`
   - **驳**：用户 reject 或提出修改 → 退回该门上游修，修完重跑该门，不得带病继续

   不要另开一个「请确认落点」的停顿——受理单**随第一道门一起受人审**。
5. **守住写权限**——按「写权限与证据」表执行，**都不允许「就地改到通过」**：

   - `checklist`：清单由评审者在门 1 勾选；`implement` 前只读复核，发现有未勾就**停下来问**，不得自己打勾
   - `analyze`：只写 `03-tasks.md` 的「analyze 交叉检查」节，不改任何被检查内容
   - `converge`：只追加任务，不得改代码或文档正文让它通过
6. **漂移先分类再动作**——发现「文档与实现不一致」时，**不是所有漂移都改文档**（三类对照表只在 `references/drift.md` 维护一次）：

   - **需求漂移**（验收场景变了）→ 改 spec → 走门 1 → 全流程重走
   - **实现漂移**（需求没变，实现没做到或做成了别的）→ 改实现
   - **放错位置的漂移**（漂移的是本该属于 plan 的实现细节）→ 搬到正确文档，**spec 不动**

   第三类最容易被误判：「spec 写 GPIO21、实现是 GPIO19」的正确动作，是**把那行从 spec 删掉**搬进 plan，而不是改 spec 去对齐实现。
7. **维护任务状态**——三种状态：`[ ]` 未完成 ｜ `[x]` 已完成 ｜ `[~]` 已作废。作废一个任务时三处同时标记：原任务行标 `[~]`；原任务内容加删除线（**任务号与 FR 编号留在删除线外**）；下方一行 `⤷` 说明被谁取代、为什么。

   ```markdown
   - [~] T026 [P] [US1] ~~面板 WS2812（busy/pass/fail/off 四态一次性设置）~~ | FR-040/041
         ⤷ r2 作废：灭态废除、busy 改蓝，被 T034 取代
   ```

   同时在变更轮段登记作废清单，并用 `check_tasks.py` 校验。任务行必须以 `- [ ]` / `- [x]` / `- [~]` 开头且任务号紧跟状态——其它写法会被校验器静默漏计，`Done When` 就失去意义。
8. **范围裁剪**——裁掉或延期一个需求等于需求范围变了，即 **spec 落点**，一律走门 1。**FR 编号不重用**：原地标 `Deferred`（延期）或 `Cut`（不做），**绝不删号、绝不重分配**；写明**理由 + 裁决人 + 日期**；相关任务标 `[~]` 并注明「范围裁剪」。
9. **异常路径**——**门 reject**：退回该门上游修，修完重跑该门，不得带病继续。**converge 不收敛**：每轮发现数必须**严格递减**，某轮不降反增就立即停下回上游（在打转 → 回上游查 spec / plan）。**blocked**：显式标记，写明卡在哪、等谁、等信息，不假装完成。
10. **禁止静默猜测**——spec 层不确定就标 `[NEEDS CLARIFICATION]`，不许猜；执行层不确定就标 `blocked`，不许猜。

## Output

- 更新后的文档集 `SDD/`：按落点重走后的 `01-spec.md` / `02-plan.md` / `03-tasks.md`，以及新增的变更轮段与受理单
- 按任务清单完成的代码变更：任务逐条勾选 `[x]`，作废的标 `[~]` 并登记进作废清单
- `04-converge.md`：收敛报告与变更轮处置记录，结论为 `Converged`（除追加外 `tasks.md` 逐字节不变）或「Tasks appended」（追加任务后回 implement）
- **`Done When`**：`tasks.md` 中所有任务均为 `[x]` 或 `[~]`（无 `[ ]`），且实现已对照规格、方案与测试覆盖完成验证
