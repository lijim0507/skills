# 规范驱动开发（SDD）

## Description

用「先文档后代码」约束一切会改动代码的工作。三条内核，其余规则都是它们的推论；看到一条规则时，先问它从哪条内核推出来，推不出来的多半是不该有的补丁。

1. **先文档后代码**——任何要改代码的事，先把文档改掉，再动代码。这是整套机制的支点：没有文档 diff，落点就推不出来。
2. **文档各有边界**——`01-spec.md` 只写 what/why（零技术），`02-plan.md` 只写 how，`03-tasks.md` 只写任务。边界守住了，「落点」才是事实而不是判断。
3. **人保留否决权**——门 1、门 2、验收由人裁决；agent 负责发现，人负责裁决。

## When to use

适用于：

- 会改动代码、且值得留下规格痕迹的变更：新增功能、修改行为、修缺陷、重构
- 需求变更、方案变更、范围裁剪
- 项目第一次用：还没有 `SDD/` 目录，需要铺纸
- 用户提到「按 SDD」「规范驱动」「先写规格」

## When NOT to use

不适用于：

- 纯问答、代码解释、只读操作（看日志、搜代码、读文件）
- 与代码变更无关的文档整理与格式调整
- **规模下限**：单文件、不改变任何外部可观察行为的小改（错别字、注释、日志文案、格式化），且用户没有点名要走 SDD——直接改
- 用户明确表示这个项目不建文档集

## Input

- **变更请求**（必填）：要改什么、为什么改。含糊时标 `[NEEDS CLARIFICATION]`，不要猜
- **目标项目**（可选）：默认当前工作目录。文档集是项目根下的 `SDD/`；已存在就先读它，不重建
- **约束**（可选）：期限、兼容性、硬件资源
- **既有文档集**（可选）：有就沿用，**不新开一套**

## Instructions

文档集（项目根下的 `SDD/`，建项时落一套，之后所有改动都在同一套上改）：

```text
SDD/
├── 00-constitution.md      项目原则：编号 · 可判定 · 注明出处
├── 01-spec.md              what/why + 门1清单与结论 + 修订记录
├── 02-plan.md              how + 门2清单与结论 + 修订记录
│   ├── 02-plan-research.md     Phase 0：每个决策 + 被否决的方案
│   ├── 02-plan-data-model.md   Phase 1：实体、状态迁移
│   └── 02-plan-contracts.md    Phase 1：接口契约
├── 03-tasks.md             任务 · 覆盖映射 · analyze 交叉检查 · 开工前检查 · 收敛追加段 · 修订记录
└── 04-converge.md          本轮收敛结论
```

落点表——改了哪份文档，就从对应的门开始往下走：

| 动了什么               | 从哪重走                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `00-constitution.md` | 宪法修订 → 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收 |
| `01-spec.md`         | 门1 → 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收             |
| `02-plan*.md`        | 门2 → tasks → analyze → 开工前检查 → implement → converge → 验收                    |
| `03-tasks.md`        | 开工前检查 → implement → converge → 验收                                               |
| 只动代码               | converge → 验收                                                                          |
| 同时动多份             | 取最上游那一处                                                                            |

按这个顺序执行：

1. **先铺纸**——没有 `SDD/` 就用 `templates/` 落骨架：把 `00` ~ `04` 写进项目的 `SDD/`，**删掉模板里的示例段**，然后继续第 2 步。
2. **判落点**——这次改动动了哪份文档？同时触及多份取最上游。判不准按上游：代价不对称——需求变更溜过去是失控，多走一遍只是浪费。
3. **写 `01-spec.md`**——范围与目标 → 用户故事（优先级 / 为什么是这个优先级 / 独立可验证 / Given-When-Then 验收场景）→ 边界与异常 → `FR-001`（MUST 句式，挂到故事）→ 成功标准（可度量、技术无关）→ 假设与未决项 → 门 1 清单与结论 → 修订记录。**本文件里出现引脚号、通道、类型名、参数值就是写错地方了**，它们属于 `02-plan.md`。
4. **停门 1**——审的是「每条需求能不能判做没做到」。四步做完，别只说一句「请批准」就往下走：
   - **停**：不在同一步里继续改下游文档或代码
   - **请**：说出「请审批门 1：approve / reject」，然后**结束本轮**等回话
   - **记**：只有回话里出现明确批准时才写 `approve ｜ 裁决人：<用户> ｜ 日期：<当天>`；**裁决人写用户，不写你自己**。没表态或「你看着办」→ 保持 `待审`
   - **驳**：reject → 退回 `01-spec.md` 修，修完重跑门 1，不得带病继续
5. **写 `02-plan.md`**——技术上下文 · 硬件 / 资源分配 · 验证手段 · 宪法检查（逐条对答 `00-constitution.md`）· 复杂度跟踪 · 待办与偏差登记 · 门 2 清单与结论 · 修订记录；Phase 0/1 子件按需产出（research / data-model / contracts）。**不重复 `01` 的需求**；需求有变化回 `01` 改，不在这里私了。
6. **停门 2**——同第 4 步的四步；审的是「方案可行吗、逐条对答过宪法吗」。reject → 退回 `02-plan*.md` 修。
7. **拆 `03-tasks.md`**——每条任务挂 `FR-0xx`，或显式标 `| 流程`（建档、清理等非需求任务）。粒度判据：**一个不知道来龙去脉的执行者，只看这一条任务，能做完并自己判定做完没做完。**
8. **跑 `analyze`**——跨产物互查。**只写「analyze 交叉检查」节**，不改被检查内容；发现问题回上游修（需求回 `01`、设计回 `02`、任务回 `03`），**未闭合项必须严格递减到 0**。某轮不降反增 → 立即停下回上游，说明在打转。
9. **过开工前检查**——评审者勾：每条 FR 有任务覆盖、依赖无环、验收手段可执行。`implement` 对它**只读**：发现有未勾就**停下询问**，不得自己打勾。
10. **`implement`**——按任务写代码，逐条把 `[ ]` 改成 `[x]`。
11. **跑 `converge`**——**只追加**：有缺口就往 `03-tasks.md` 的「收敛追加」段追加任务，然后回第 10 步；无缺口 → `Converged`（判据：除本次追加外 `03-tasks.md` 逐字节不变）。结论写进 `04-converge.md`。
12. **停验收**——`converge` 只证「代码没背叛文档」，证不了「板子上真的做到了」。由人按 `01-spec.md` 的验收场景在**真实设备**上跑一遍并签字，结论落 `04-converge.md`。**这一步没有替代品。**
13. **守住写权限**——**都不允许「就地改到通过」**：门结论只由裁决人写；`analyze` 只写自己那一节；`converge` 只追加任务、不改代码与文档正文。
14. **记账只记 diff 看不到的**——改了什么 diff 里有；修订记录写**为什么、依据什么、谁批的**。一次改动跨多份文档时，用同一个轮次号（`r2`）串起来。
15. **措辞订正免门 1**——改的是 `01-spec.md` 的措辞、功能全量等价（术语统一、错别字、把含糊句写清楚）→ 不算需求修订，只在修订记录留一句「语义未变」。这条豁免靠「验收场景段落逐字节未变」兜底，拦不住换了说法的语义漂移。
16. **不确定就显式标**——需求不确定标 `[NEEDS CLARIFICATION]`，执行不确定标 `blocked`，写明卡在哪、等谁，不许静默猜测。

状态图（第 1 ~ 12 步的压缩）：

```text
S0 没有 SDD/ → 用 templates/ 落骨架，立即进流程
  ↓
S1 01-spec ──🚦门1── approve → S2 ／ reject → 回 S1
  ↓
S2 02-plan（含 Phase 0/1 子件、宪法逐条对答）──🚦门2── approve → S3 ／ reject → 回 S2
  ↓
S3 03-tasks（每条任务挂 FR）
  ↓
S4 ⚙️ analyze ── 未闭合项必须严格递减到 0；发现问题 → 回上游修
  ↓
S5 ⚙️ 开工前检查 ── 全勾 → S6 ／ 有未勾 → 停下问
  ↓
S6 implement ── 任务 [ ] → [x]
  ↓
S7 ⚙️ converge ── 有缺口 → 追加任务 → 回 S6 ／ 无缺口 → S8
  ↓
S8 🚦 验收 ── 按 01 的验收场景在真实设备上跑一遍，人签字
  ↓
完成
```

细则：`references/doc-set.md`（文档职责与内容归属）｜`references/landing.md`（落点与记账）｜`references/gates.md`（关卡规则、写权限、停机动作）｜`references/roles.md`（角色分工与多 agent）｜`references/checks.md`（机器检查与脚本用法）。

脚本在**技能目录**里，不在目标项目里。运行：`python <技能目录>/scripts/check_spec.py <项目>/SDD/01-spec.md`（规格结构）｜`check_tasks.py`（任务与开工前检查）｜`check_chain.py`（故事 → FR → 任务不断链）。

## Output

- 更新后的文档集 `SDD/`：按落点重走后的 `01-spec.md` / `02-plan*.md` / `03-tasks.md` / `04-converge.md`，以及各文档的修订记录
- 按任务清单完成的代码变更：任务逐条勾选 `[x]`
- `04-converge.md`：本轮收敛结论（发现了什么、怎么处置、结论是 `Converged` 还是 `Tasks appended`）
- **Done When**：`03-tasks.md` 无 `[ ]` 残留，且验收已按 `01-spec.md` 的验收场景在真实设备上跑过、由人签字
